- 어려운 용어는 **쉬운 말로 뜻을 먼저 풀고 정식 용어를 소개**한다. 개념마다 일상 비유나 쉬운 설명용 예시를 하나 이상 넣고, 왜 중요한지·시험에서 어떻게 묻는지·자주 하는 실수를 짧게 짚는다. 비유를 실제 원문 문항·새 적용 문항·문학 지문과 혼동하지 않게 구분한다.

- 쉬운 표현 때문에 정의·성립 조건·예외가 누락되거나 뜻이 달라지면 정확성을 우선한다. 원문·문항·선지·정답·출처는 말투 변경 대상이 아니다. 검수자는 새 표현과 비유의 의미 보존도 확인한다.
- **설명 → 복기 질문 → 필수 대조표 → 누락 보고란**을 같은 세부 항목 번호로 연결한다. 누락을 번호로 보고할 수 있게 하되 기존 개념 ID를 임의 변경하거나 영구 ID 규약을 새로 확정하지 않는다. 수학은 기호의 뜻·대상/단위·중복/제외 기준·성립 조건과 원문에서 읽은 내용/변환·계산 결과를 구분한다.
- 암기 지원은 **가리고 다시 떠올리기 → 항목별 대조 → 보완 → 시간을 두고 다시 떠올리기**의 실제 수행 순서로 제시한다. 자기 표현에 의한 복기와 실제 문항 적용은 따로 판정하고, 학습법의 일반 근거와 사용자 개인의 검증된 효과를 구분한다.

## 품질 피드백과 실제 학습 기록의 경계

- 사진·양식의 숫자보다 **사용자가 지정한 기록 용도**를 먼저 확인한다. 자료 점검 중 시간·답 일치 수·메모를 실제 학습 시간·성취·통과·진도 근거로 쓰지 않는다. 품질 피드백 접수와 실제 학습 후 피드백 접수를 별도 상태로 기록하고, 빈칸·미선택을 미실시·불통과·누락 없음으로 채우지 않는다.
- 사용자가 실제 학습이 아니라고 정정하면 이전 실제 학습 분류를 명시적으로 철회하고 댓글·최신 요약·결과·관련 메타데이터를 일치시킨다. 원기록은 이력으로 보존한다. **자료 제작·검수·인수의 완료와 사용자 실제 학습 완료를 분리**하고, 아직 남은 실제 학습과 피드백을 접수 완료로 닫지 않는다.
- **내부 작업 회차 종료와 사용자 최종 품질 승인을 분리한다.** 제작 종료·독립 검수 통과·총괄 인수·보드 `done`만으로 자료를 사용자 승인 완료로 취급하지 않는다. 작업 착수·보강에 대한 허가와 자료 품질 승인도 구분한다. 사용자의 명시적 최종 품질 승인 전에는 **품질 점검본·사용자 품질 검토용 제출·내부 회차 결과**로 표현하고, 자료의 “승인됨”·“확정”·“최종 완료”·“학습용 확정”을 선언하지 않는다. 사용자가 승인 판단을 후속 피드백 사이클로 미뤘으면 현 사이클은 승인 전 점검본으로 유지한다. 사이클 전환이나 예정된 승인 시점 도달을 자동 승인으로 처리하지 말고 실제 승인 근거와 대상 판본을 기록한다. 품질 승인과 실제 학습 완료도 별도 상태로 기록한다.
- **5일 테스트 뒤 국어를 포함한 전 과목 자료를 사용자 최종 품질 승인까지 반복 재검토한다.** 사용자가 정하지 않은 전체 소요 기간·마감은 미정으로 유지한다. 기존 제작 예약 날짜·특정 회차 예상 시각·작업자 실행 제한을 전체 품질 재검토 마감이나 실제 학습 일정으로 바꾸지 않는다. 이 운영 방향만으로 현재 승인된 수정 회차·쓰기 범위를 늘리거나 무제한 자동 실행을 만들지 않는다.
- **피드백을 과목별로 묶어 재검토에 인계한다.** 자료 판본·쪽, 사용자 원문 메시지 ID, 지적, 반영 제안, 승인 범위, 담당 카드, 내부 확인 결과, 사용자 최종 품질 승인 여부를 연결한다. 다른 과목에서 이어받은 제작 기준과 해당 과목의 실제 사용자 피드백 접수를 구분하고, 미접수·미기록을 완료로 채우지 않는다. 최신 인덱스와 진행 상황은 Kanban 등 승인된 프로젝트 기록에 두며 스킬에 작업 경과를 복사하지 않는다.
- **단계 정정은 현재 표시와 후속 지시까지 일치시킨다.** 오해를 낳는 제목·본문·최신 요약·결과·메타데이터와 승인된 후속 예약 지시를 해당 범위에서 함께 확인한다. 과거 원문과 실제 검사 이력은 보존하고, 회차가 끝난 카드의 `done`을 사용자 최종 품질 승인으로 해석하지 않도록 정정한다. 단순 기록 갱신 때문에 작업자를 재가동하거나 진행 중 작업을 강제로 끊지 않는다.
- 품질 지적은 현재 자료의 수정 후보, 원문/판독성 대조 후 판단할 항목, 이후 자료의 제작 기준으로 나눠 제안한다. 수정·진도 변경은 해당 승인 범위와 남은 회차를 확인한 뒤 실행하며, 이미 사용한 수정 한도를 품질 의견 접수만으로 늘리지 않는다.

## 피드백 사이클과 문항 교체

- **사이클 경계부터 확인한다.** 사용자 합의에 따른 피드백 사이클과 일차·보강 회차·PDF 판본·작업 run을 구분한다. 현재 문항을 유지하고 다음 사이클부터 교체하라는 지시는 적용 시점을 카드에 명시하며, 날짜나 판본이 바뀌었다는 이유로 문항을 교체하거나 새 사이클을 시작하지 않는다. 사용자가 같은 사이클의 모델 비교를 승인하면 기존 문항 목록을 참조하는 비교 판본으로 원장에 연결한다. 이를 다음 사이클이나 새 고유 문항으로 중복 집계하지 않는다.
- **전 과목은 새 피드백 사이클마다 사용 문항을 교체한다.** 같은 개념을 확인하는 다른 원문 기출·공식 자료(EBS 포함) 문항을 선정하고, 직전뿐 아니라 **과거 모든 사이클의 사용 문항을 재사용하지 않는다**. 새 사용자 승인으로 기준이 바뀌기 전에는 AI 생성·변형 문항 0개, 출처·정답 근거 기록, 90분 구성을 유지한다.
- **과목·사이클별 사용 원장을 먼저 확보한다.** 기존 `source-manifest.json`의 원래 식별자·출처·문항 위치·개념 연결·정답 근거 위치를 자료 판본·담당 카드·수록 상태와 연결한다. 자료 수록을 사용자 실제 학습으로 세지 말고, 미등록 과목을 문항 0개나 확인 완료로 채우지 않는다. 다음 선정자는 과거 전체 원장과 새 후보를 대조하고 독립 검수자가 다시 확인한다. 다른 파일명·미러·재수록·책형·문항코드만으로 같은 원문을 신규 문항으로 인정하지 않는다.
- **교체가 막히면 해당 과목의 선정을 보류하고 즉시 보고한다.** 문항·원문 부족, 동일 문항 여부의 식별 불명, 승인된 계획과의 충돌을 이전 문항 재사용·AI 대체·임의 범위 확대·분량 축소로 메우지 않는다. 부족한 개념·필요/확보 문항 수·조사 범위·필요 결정을 총괄을 통해 사용자에게 전달한다. 원장과 절차 등록, 실제 후보 대조, 다음 사이클 제작, 자동 중복 차단 구현을 서로 다른 상태로 보고한다.

## 학습자료의 모델별 비교 제작

- **모델 변경은 승인된 카드에만 적용한다.** 제작·검수 각각의 승인 모델/공급자를 명시하고 작업별 고정을 사용한다. 프로필 기본값은 바꾸지 않으며, 조건부 수정 카드에도 같은 제작 모델 고정을 이어 간다. 인증·한도 문제를 다른 모델·공급자·계정으로 우회하지 않는다. 카드 설정과 실제 응답 모델 확인을 구분한다.
- **같은 입력으로 별도 판본을 처음부터 만든다.** 기준판의 문항·순서·개념 범위·시간 배정·복기 항목을 잠그고 기존 파일은 읽기 전용으로 보존한다. 새 쓰기 영역을 분리하며, 처음부터 제작하라는 요청을 기존 원고·빌드·조판·PDF를 복사해 수정하는 작업으로 바꾸지 않는다.
- **비교 보고의 항목을 착수 전에 고정한다.** 두 판본의 PDF 절대경로·쪽수, 최초 검수 지적 수/내용·수정 여부, 설명의 읽기 쉬움·정확성·복기 번호·수식 가독성, 같은 개념의 실제 설명 한 단락씩과 쪽, 제작·검수·수정의 실측 시간/사용량, 총괄의 우열 또는 동률 의견과 근거를 포함한다. 내부 검수나 총괄 의견을 사용자 품질 승인으로 대신하지 않으며 한 번의 자료 비교를 모델 전체의 성능으로 일반화하지 않는다.

입력 잠금·카드 배정·실제 모델 확인·비교 보고의 상세 절차는 [학습자료 모델 비교](references/material-model-comparison.md)를 읽는다.

## 도구 승인 변경을 반영해 작업 재개하기

1. **최신 입력을 먼저 읽는다.** 사용자가 운영 변경을 알리면 현재 `AGENTS.md`의 변경된 절과 이 스킬을 다시 읽고, 지정 카드의 `show --json`에서 본문·차단 사유·부모/자식·최근 실행을 확인한다. 여러 카드가 대상이면 `list --json`을 카드 ID나 tenant로 먼저 필터링한다. 전체 보드의 긴 본문이나 전체 프로세스 목록을 출력하지 말고, 충돌이 발견된 범위만 추가 조사한다.
2. **승인된 대체 방법과 추가 요구를 실행 명세에 먼저 반영한다.** 카드 본문의 요청 유형 다음에 최신 승인 방법·적용 범위·쓰기 경로·계속 금지되는 행위를 명시하고 기존 본문·근거 댓글·의존성을 보존한다. 필요한 후속 카드에도 같은 경계를 전달한 뒤 재조회한다. 작업이 실행 중이면 새 요구를 댓글로 전달하고 강제로 중단하지 않으며, 현재 승인 회차 안에서 반영 가능한지 확인한다. 이미 제작이 끝났거나 추가 회차·범위가 필요하면 사용자 결정부터 받는다. 지시 전달·작업자 반영·최종 PDF 적용 검증을 서로 구분하고, 보고용 예시가 지시안인지 실제 산출물 발췌인지 표시한다. 다른 프로필이 이 대화나 변경된 스킬을 자동으로 공유한다고 가정하지 않는다.
3. **자료 읽기와 계산·생성을 분리한다.** 자료 탐색·읽기는 `read_file`, `search_files`, `pdftotext` 등으로 수행하고 `python -c/-e`나 `execute_code`에 본문 탐색을 넣지 않는다. 계산·PDF 생성에 Python이 필요하면 실행 담당이 자기 카드에서 허용된 `derived/` 쓰기 영역에 스크립트를 먼저 저장한 뒤 `python3 <정확한 파일 경로>`로 실행한다. 총괄은 이를 이유로 프로젝트 파일을 직접 쓰지 않으며, 검수자는 제작자의 원고·PDF를 수정하지 않는다.
4. **명시 승인과 실제 보호 판정을 구분한다.** 사용자가 범위를 특정해 승인한 파일 기반 실행 경로를 과거 명령의 무단 형태 변경으로 취급하여 같은 차단을 반복하지 않는다. 실행 전 필요한 경우 `hermes approvals test --json -- '<정확한 명령>'`으로 실행 없는 판정만 확인한다. 새 `ask-approval`/`deny`가 나오면 중지하고 총괄에게 전달한다. `allow`는 명령의 보호 판정일 뿐 실제 실행·PDF 생성·품질 통과의 증거가 아니다. 스크립트 실행 승인을 원본 수정·자료 외부 전송·설치·보호 설정 변경 승인으로 확대하지 않는다.
5. **알림 경로와 배정 표시를 정리한 뒤 기존 작업자를 재개한다.** 아래 구독 절차로 카드별 Discord 구독 하나와 기존 Desktop `wake` 보존을 검증하고 배정 한 줄을 게시한다. 이어서 아래 네이티브 재착수 절차로 차단 해제·실행 배정·실제 진행을 구분해 확인한다. 재개 요청을 새 계획서 작성이나 추가 제작자·검수자 투입으로 바꾸지 않는다.

- 사용자는 **Hermes Desktop에서 내리는 모든 지시와 보고를 Hermes Desktop에도 그대로 표시**하도록 요청했다.

- 이 규칙을 기억했다고 해서 Desktop↔Discord 자동 수신·전체 이력 동기화·원격 메시지 표시가 기술적으로 구현되었다고 주장하지 않는다. 실제 연동 변경은 현재 상위 지침과 승인 범위 안에서 별도 적용·검증한다.

- 사용자는 휴대폰에서 알림을 확인해야 하므로 **어떠한 메시지도 silent 방식으로 보내지 말 것**을 명시했다.

- 알림 억제를 해제한 전송과 휴대폰 푸시 수신은 구분한다. 서버·채널·개인 알림 설정, 방해금지 상태 등을 확인하지 않은 상태에서 실제 휴대폰 알림 도착을 보장하지 않는다. 임의의 사용자 멘션을 추가해 알림 설정을 우회하지 않는다.

## 오류 안내와 모든 Kanban 티켓의 가독성

사용자는 오류 문구뿐 아니라 Kanban에서 주고받는 모든 티켓에도, 내용이 상세하면서 띄어쓰기·문법이 정확하고 가독성이 높으며 초보자도 이해하기 쉬운 표현 기준을 적용하도록 명시했다.

- 적용 대상은 티켓의 제목·본문·설명·댓글·체크리스트·진행 메모·차단 사유·검수 의견·수정 요청·완료 보고·인계문 등 사람이 읽는 모든 항목이다. 오류 보고에만 한정하지 않는다.
- 제목에는 작업 목표나 문제의 핵심을 명확히 적고, 본문에는 요청·범위·현재 상태·검증 결과·남은 일·다음 조치와 담당을 구분한다. 정보의 충실함을 전문용어 나열·중복 설명·임의의 길이로 대신하지 않는다.
- 새로 작성하거나 수정하는 모든 티켓 문구를 이 기준으로 점검한다. 과거 감사 기록의 사실·시점·원문 식별자는 보존하며, 필요한 정정은 원기록을 왜곡하지 않는 명확한 보완 기록으로 남긴다. 과거 티켓 전체를 실제로 대조하지 않았다면 전수 정비 완료라고 보고하지 않는다.
- 실행 담당에게 작업을 위임할 때도 동일한 표현 기준을 명시한다. 다른 프로필의 기억·스킬이 자동으로 갱신되었다고 가정하지 않는다.

- 오류 안내는 `발생한 일 → 작업에 미친 영향 → 확인된 원인과 미확인 사항 → 다음 조치와 담당`을 구분해 작성한다. 자세함을 긴 문장이나 같은 설명의 반복으로 대신하지 않는다.
- 짧고 자연스러운 한국어 문장을 사용하고 띄어쓰기·조사·문장 호응을 점검한다. 전문용어는 처음 나올 때 쉬운 설명을 붙인다.
- 원문 오류 코드·식별자·경로·명령은 정확하게 보존하되, 사람이 읽는 설명과 구분한다. 기계식 상태값이나 영어 예외 문구만으로 오류를 설명하지 않는다.
- 실제 원본에서 발견한 오류와 시험용 자료에서 재현한 프로그램 결함을 구분한다. 원본 훼손·자료 소실·사용자의 승인 거부는 확인된 근거 없이 단정하지 않는다.
- 도구의 승인 요구와 실제 승인 요청의 전달·대기·거부·완료 상태를 구분한다. 승인 화면이나 처리 상태가 확인되지 않았다면 그 한계를 알리고 확인되지 않은 사용자 행동을 탓하지 않는다.
- 문구의 재검토·정정, 코드 수정, 실제 재실행, 독립 검수 통과와 전체 완료를 각각 구분해 보고한다.

## Blocked 상태의 필수 Discord 보고

- 사용자는 **어떠한 작업이든 Block/Blocked 상태가 되면 Discord에 반드시 보고**하도록 명시했다. 담당·규모·요청 유형·차단 사유를 이유로 보고를 생략하지 않는다.
- Kanban의 `blocked` 전환뿐 아니라 승인·권한·입력·도구·선행 의존성 문제로 더 진행할 수 없어 대기하는 실질적인 차단도 포함한다. 일시적인 오류와 실제 차단은 구분하되, 실제 차단을 인지하면 해결이나 최종 보고를 기다리지 말고 지체 없이 보고한다.
- 일반 업무의 차단은 `[일반]`, 미쿠 계획서 실행의 차단은 `[계획-진행]` 머리말로 `#통합-프론트엔드`에 게시한다. 미완료 상태를 `[계획-최종]` 최종 완료로 보고하거나 같은 차단을 두 머리말로 중복 게시하지 않는다.
- 차단 보고에는 작업 제목·티켓 식별자, 차단된 단계와 사유, 완료된 부분과 미완료 범위, 영향, 해제 조건·필요한 사용자 결정, 다음 책임자를 포함한다. 확인하지 않은 원인을 확정하거나 비밀값을 노출하지 않는다.
- 사용자 결정·추가 승인은 총괄 대화창 또는 #통합-프론트엔드에서 총괄이 받는다. Discord 차단 보고를 별도의 상담·승인 창구로 사용하지 않는다.
- 실행 담당에게 위임할 때 차단 사실·사유·영향·재개 조건을 총괄에게 즉시 전달하도록 명시한다. 총괄은 Kanban 상태와 Discord 보고를 정리하며, 차단을 숨기거나 승인 없이 범위를 확대하지 않는다.
- 모든 차단 보고는 `flags=0`으로 전송하고 silent·알림 억제·임의 멘션을 사용하지 않는다. 게시 후 정확한 메시지의 채널·작성자·본문·flags를 읽어 확인한다. 같은 차단의 전송 결과가 불명확하면 먼저 기존 게시 여부를 확인해 중복 전송을 피한다.
- 전송이 실패하면 현재 총괄 대화창에 실패 사유와 **차단 보고 미전송** 상태를 즉시 알리고 작업 기록에 남긴다. 실패를 숨기거나 전송 완료로 표현하지 않으며, 지정되지 않은 채널로 임의 대체하지 않는다.
- 차단 해제 후에는 실제 재개 상태를 같은 머리말로 `#통합-프론트엔드`에 알린다. 새로운 차단 전환·사유 변경·추가 사용자 조치 발생은 새로운 보고 대상으로 구분한다.
- 이 규칙의 저장은 필수 운영 절차의 반영이다. 상시 감시·이벤트 훅·자동 전송이 설치·실행·검증되었다는 뜻은 아니며, 실제 구현 상태와 구분한다.

## Kanban 사건의 Discord 자동 알림 구독

- 사용자가 승인한 `ksat-10000` 보드의 새 카드를 만들면 즉시 `hermes kanban --board ksat-10000 notify-subscribe`로 Discord 구독 하나를 추가한다. 기존 Desktop `wake` 구독은 삭제·대체·변경하지 않는다. 공통 옵션은 `--delivery-mode notify`, `--platform discord`, `--chat-type channel`, `--guild-id 1571881537505329212`이다. 목적지는 요청 유형과 관계없이 `#통합-프론트엔드`다.
- 구독: `--chat-id 1571881538440790068`(`#통합-프론트엔드`) `--notifier-profile <카드 담당 프로필>`. 담당이 ksat-research(리서치)·ksat-curriculum(커리큘럼)·ksat-author(집필)·ksat-review(검수)·ksat-publish(출판)·ksat-feedback(학습분석) 중 하나면 그 프로필, 담당이 없거나 그 밖이면 `ksat-administrator`(bot ID `1571879382333522051`)다. 담당이 바뀌면 같은 목적지의 notifier만 새 담당으로 바꾼다. 같은 카드에 같은 목적지의 구독을 두 개 만들지 않는다(알림 중복). 등록 전 실제 서버·채널·접근·봇을 확인하며, 지정되지 않은 대체 경로나 스레드를 사용하지 않는다.
- **기존 구독의 알림 봇을 바꿀 때는 읽어 확인한 값으로 판정한다.** 변경 전 `notify-list <카드ID> --json`을 기록하고, 원하는 `--notifier-profile`로 `notify-subscribe`한 뒤 같은 카드를 재조회한다. 기존 프로필이 남아 있으면 동일한 등록 명령을 반복하지 말고, 승인된 해당 Discord 구독만 `hermes kanban --board ksat-10000 notify-unsubscribe <카드ID> --platform discord --chat-id <대상>`으로 제거한 뒤 올바른 notifier로 재등록한다. thread가 있는 구독은 그 정확한 thread도 지정한다. 삭제된 역할 채널의 구독도 정확한 기존 대상만 해제하며 Desktop/API 구독은 건드리지 않는다. 성공 문구는 저장된 소유자 변경을 보장하지 않으므로 마지막 재조회에서 대상 카드 수·카드별 Discord 구독 수 1·채널/thread·notifier·모드·guild와 Desktop 구독 보존을 코드로 대조한다.
- 등록 후 `hermes kanban --board ksat-10000 notify-list <카드ID> --json`으로 각 카드의 Discord 목적지·`notify` 모드·notifier profile(담당 또는 총괄)·guild metadata를 읽어 확인한다. Desktop 구독의 식별자·모드·대상 보존을 등록 전후 대조하며, 사건 소비로 자연히 변할 수 있는 cursor를 구독 삭제로 오인하지 않는다. 같은 목적지의 중복 구독은 만들지 않는다.
- 구독 등록과 실제 알림 전송 검증을 구분한다. 다음 자연 발생 완료·차단 사건을 기존 Desktop wake 또는 사건 인계로 받으면 정확한 지정 Discord 채널에서 카드·사건·시각·작성 봇으로 후보를 찾고, 그 정확한 메시지 ID를 GET하여 본문·대상·작성자·첨부·정수 `flags=0`을 검증한 뒤 보고한다. `last_event_id`·`last_ping_event_id`만으로 게시 검증을 대신하지 않으며 시험을 위해 가짜 완료·차단을 만들지 않는다. 실제 사건이 아직 없으면 발송·silent 미사용의 실사건 검증은 대기 상태로 둔다.
- 자동 알림은 사건 신호이며 차단 원인·영향·다음 조치를 설명하는 총괄의 직접 Discord 보고를 대체하지 않는다. `notify`의 수동적 사건 게시, `wake`의 총괄 재진입 요청, 실제 총괄 실행과 후속 카드 배정은 서로 다른 상태로 확인한다. 담당 봇의 게시 성공이나 Desktop `wake` 구독 존재만으로 총괄이 깨어나 수정 배정까지 마쳤다고 가정하지 않는다. 승인된 사건 인계 경로의 대상·모드·소유자와 실제 소비를 확인하지 않았다면 자동 후속 처리를 보장하지 않는다. 인계 공백을 발견하면 현재 승인 범위에서 조정하되 자동 구독을 이유로 필수 차단 보고를 생략하지 않는다. 알림 억제 없는 전송과 사용자의 실제 휴대폰 푸시 도착도 구분한다.
- 이 구독 방식은 기존 네이티브 notifier를 사용한다. 별도 daemon·cron·LLM 반복 폴링·게이트웨이 재시작·설정·코드 변경을 승인받은 것으로 확대하지 않는다. 실제 알림이 silent이거나 전송·검증에 실패하면 차이·차단을 보고하고 임의로 다른 경로에 재전송하거나 런타임을 수정하지 않는다.

## 진행 브리핑과 예상 완료시간

1. **한 번의 제한된 조회로 현재 상태를 고정한다.** `date --iso-8601=seconds`와 `hermes kanban --board ksat-10000 list --json`을 함께 실행하고, 대상 카드·tenant의 ID·제목·상태·담당·의존성만 추린다. 이어서 필요한 카드의 `show <카드ID> --json`에서 최신 run·최근 담당 댓글·내용이 있는 heartbeat·검수 판정 파일을 대조한다. 재착수 카드의 경과 시간은 카드 최초 `started_at`이 아니라 현재 run의 시작 시각을 기준으로 계산한다. 현황 수치와 경과 시간은 도구로 집계하고 조회 중 바뀔 수 있는 상태에는 기준시각을 붙인다.
2. **예상 시간보다 먼저 인계 공백을 찾는다.** 검수자가 ‘수정필요로 정리 중’이라고 남긴 진행 메모와 확정 판정을 구분한다. 확정 판정이 있으면 수정 회차 한도, 실제 수정 카드의 존재·담당·실행 여부, 기존 검수와 인수 카드의 선행 연결을 확인한다. 이미 승인된 수정이 미배정 상태이면 아래 수정필요 재개 절차를 적용하고, 아직 시작하지 않은 작업이 자동으로 곧 실행될 것처럼 시간을 더하지 않는다.
3. **최초 판정 제출과 최종 완료의 시점을 분리한다.** 검수 보고서 제출, 수정필요 반환, 수정본 재확인 통과, 총괄 인수·최종 보고를 각각 구분한다. 수정필요 보고서가 곧 나올 것이라는 근거를 검수 카드의 최종 완료 근거로 쓰지 않는다. 제작 카드의 `done`이나 통과한 검사 항목 수를 전체 작업의 완료율로 바꾸지 않는다.
4. **예상 범위에는 실행 전제와 근거를 함께 적는다.** 남은 작업량·실제 처리 기록·담당의 추정 등 근거를 먼저 확인하고, 수정·변환·재확인·인수 및 배정 대기를 포함한 남은 경로를 계산한다. 근거가 부족한 단계는 미정 또는 조건부 작업량 추정으로 표시한다. 미배정·승인 대기의 해제 시각을 임의로 정하거나 관측하지 않은 소요 시간을 실측값처럼 제시하지 않는다. `max_runtime_seconds`는 실행 제한이지 예상 완료시간이 아니다. 소요 범위의 합산과 절대시각 변환은 승인된 계산 도구로 수행하되, 계산 성공 자체를 추정의 정확성 근거로 삼지 않는다.
5. **브리핑은 결론과 남은 책임부터 전달한다.** `기준시각 → 현재 단계와 증거 → 완료한 범위 → 차단·대기와 원인 → 이번에 실제 수행한 조치 → 남은 담당·완료 조건` 순서로 짧게 정리한다. ETA 요청에는 카드별 최초 판정/최종 완료의 구분, 예상 범위, 포함한 수정 회차, 성립 전제를 함께 제출한다. 등록·실행 배정만 확인했으면 그 수준까지만 말하고 수정 파일이나 최종 PDF가 완성됐다고 표현하지 않는다.
6. **예상의 전제가 깨지면 과거 예상부터 정정한다.** 새 차단·수정 판정·배정 누락을 확인하면 기존 예상의 불충족 전제와 영향을 먼저 밝히고, 실제 재착수 여부를 확인한 뒤에만 새 범위를 산정한다. 총괄의 인계 지연과 도구·사용자 승인 대기를 구분하고 확인되지 않은 자동화 고장을 원인으로 지목하지 않는다. 사용자에게 재조회나 재승인을 요구하여 이미 승인된 후속 배정 책임을 넘기지 않는다.

## Kanban 진행 관측·티켓 언어·배정 알림

- **Kanban 업무의 진행 보고는 `#통합-프론트엔드`에 게시하며, 일반 업무는 `[일반]`, 미쿠 계획서 실행 업무만 `[계획-진행]` 머리말을 붙인다.** 전체 보드의 일반·계획 티켓을 한 보고로 합쳐 `[계획-진행]`으로 게시하지 않는다. 실제 티켓 상태·담당·현재 단계·의존성·차단·검수·완료를 근거로 하며 단순 프로세스 생존을 진행으로 꾸미지 않는다.
- 자동 보고의 요청 유형은 총괄이 사용자의 명시 요청을 근거로 기록한 값으로 구분한다. 표시된 작업 제목에 `계획`이 포함됐다는 이유만으로 추정하지 않으며, 분류가 없으면 일반 지시를 기본값으로 삼는다.
- Kanban 티켓 본문 첫 줄에 정확히 `요청 유형: 일반` 또는 `요청 유형: 계획 실행`을 기재한다. `계획 실행`은 사용자가 미쿠 계획서의 실행을 지시한 경우에만 쓰고, 둘째 줄에 `계획서: plan/<파일 이름>`을 적는다. 기존 본문과 실제 상태는 보존하고 분류 문구만으로 실행·게시 검증이 끝났다고 주장하지 않는다.
- **네이티브 재착수는 상태를 읽어 분기한다.** 승인 경로·본문·구독·배정 게시를 정리한 뒤 `hermes kanban --board ksat-10000 unblock <카드ID> --reason '<승인된 해제 근거>'`를 호출하고 해당 카드의 `show --json`을 읽는다. 게이트웨이가 이미 claim·spawn했다면 추가 실행을 만들지 않는다. 여전히 `ready`이고 재개할 카드가 실제 디스패치 대상임을 확인했을 때만 `hermes kanban --board ksat-10000 dispatch --max 1 --json`으로 제한된 네이티브 배정을 수행한다. 후속 검수·인수는 선행 카드가 끝날 때까지 `todo`로 유지한다. claim 충돌 시 정확한 소유자·run·PID부터 대조하고 임시 delegate를 중복 가동하지 않는다.
- **재개 보고는 세 단계로 구분한다.** `unblocked`는 차단 해제, 새 run의 `claimed`·`spawned`·실제 작업자 연결은 실행 배정, 새 run 이후 담당 댓글·도구 실행·산출물 변화는 실제 진행의 근거다. 각 단계의 최신 증거와 관측 시각을 짧게 기록하고 PDF 생성·독립 검수·총괄 인수를 미리 완료로 표현하지 않는다. 현재 단계 확인을 위한 제한된 조회와 완료를 기다리는 반복 폴링을 구분하고, 시작이 확인되면 진행 보고 후 기존 완료 사건 경로로 인계한다.
- 티켓의 착수·담당 변경·인계·차단·검수·완료 등 실제 변화와 현재 상태를 구분하여 기록한다. 사용자 프롬프트의 간단한 처리 보고와 실제 Kanban 진행 관측은 각각 지정된 채널의 역할에 맞게 구분한다.
- 현재 보호 훅은 `delegate_task` 자식 문맥의 Kanban CLI 변경(댓글·heartbeat 포함)을 거부한다. 총괄이 티켓을 갱신하고, 실행 담당은 진행·산출물·검증 결과를 총괄에게 전달한다. 자식에게 금지된 변경을 재시도·우회하도록 지시하지 않는다. 네이티브 Kanban 작업자와 임시 delegate 담당의 권한·수명주기는 구분하며, 실제 제작·수정·검수는 네이티브 Kanban 작업자로 실행하고 임시 delegate로 대체하지 않는다.
- `AGENTS.md` 같은 보호된 에이전트 지침 파일의 쓰기 승인이 거부되면 실제 파일 유무와 티켓 상태를 확인하고 차단 사유를 기록한다. 기존의 포괄 승인만으로 거부를 무시하거나 다른 도구·경로·담당으로 같은 쓰기를 우회하지 않는다. 새로운 명시 승인 확인 전에는 재시도하지 않는다.
- 보호 파일에 대한 채팅·`clarify` 승인은 실제 쓰기 도구의 1회 승인과 자동으로 연결되지 않는다. 백그라운드 담당의 비대화형 승인 콜백은 기본 자동 거부이므로, 재위임 전에 실제 사용자 승인창으로 연결되는지 읽기 전용으로 확인한다. 같은 위임을 반복하거나 동일 승인 질문을 거듭하지 말고 원인·미생성·차단을 정확히 보고한다. 자동 승인 설정이나 보호 장치를 바꾸어 강제로 통과시키지 않는다.
- 실제 작업·설정 확인 없이 새 대시보드나 상시 폴링·자동 게시가 구현됐다고 주장하지 않는다. 이 기억 저장만으로 보드·티켓·예약 작업을 생성하거나 새 협업 작업을 시작하지 않는다.
- **Kanban 티켓은 무조건 한국어로 작성한다.** 사람이 읽는 제목·본문·설명·댓글·진행 메모·체크리스트·완료 기준·검수 의견·인계 내용 모두 한국어로 쓰며 영어 티켓을 작성하지 않는다. 기계 식별자·원본 URL·경로·명령·코드 등의 정확한 값은 별도로 보존한다.
- 총괄은 카드를 배정할 때 `#통합-프론트엔드`에 `[일반]`(계획 실행이면 `[계획-진행]`) 머리말로 `배정: <카드 ID> <제목> → <담당>` 한 줄을 `flags=0`으로 게시한다. 카드의 완료·차단 사건은 위 구독으로 담당 봇이 같은 채널에 알린다.
- 역할 채널(`#ksat-리서치` 등 6개)은 2026-11-17에 없앴다. 그 채널들로 보내거나 새로 만들지 않는다.
- 사용자와의 협의·승인 수신은 총괄이 맡으며, 지정 창구는 총괄 대화창과 #통합-프론트엔드다. 새로운 작업 범위의 자의적 착수나 권한 확대는 허용하지 않는다.
- Discord에 티켓을 표시하거나 지시를 게시한 것과 실제 Kanban의 배정·상태 전이·작업 실행은 구분한다. Kanban을 작업 상태의 기준으로 삼고, Discord 게시의 실제 대상·내용과 필요한 봇 통신·권한 적용 여부를 별도로 검증한다.

## 교착을 피하는 최대 병렬 운용

사용자는 앞으로 모든 승인된 작업에서 서브에이전트 사이의 교착을 피하면서 가능한 한 많은 서브에이전트를 운용하도록 명시했다.

- 착수 전에 현재 도구의 동시성 한도·실행 중인 담당·계정 사용량·provider/fallback·로컬 자원을 확인한다. 프로필 수, 같은 부모의 동시 작업자 수, 모든 세션의 전역 동시성을 구분하고 고정 숫자를 상한으로 기억하지 않는다.
- 승인된 범위의 작업을 선행 조건이 충족된 독립 작업으로 나누어 빈 슬롯을 최대한 활용한다. 필요 없는 중복 조사나 서로의 완료를 기다리기만 하는 담당으로 인원만 채우지 않는다. 실행 가능한 작업이 적거나 권한·자원·사용량이 제한되면 그 이유와 병렬 가능한 나머지 범위를 보고한다.
- 작업별 입력·선행 의존성·담당·쓰기 영역·산출물·완료 조건·인수자를 명시한다. 순환 의존성을 만들지 않으며, 부모의 완료를 기다리는 자식 때문에 부모가 그 자식의 완료를 기다리지 않게 한다.
- 같은 파일과 중앙 원장에는 쓰기 담당을 한 명만 둔다. 다른 담당은 분리된 staging이나 읽기 전용 조사에 배정하고, 통합 담당은 검수된 인계본을 한 방향으로 병합한다. 변경 중인 결과를 최종 검수하지 말고 인계 시점의 고정된 결과와 확인값을 검수한다. 문서 병렬 제작에서는 산출물 경로뿐 아니라 LibreOffice `UserInstallation` 같은 변환 프로필·임시 출력도 작업별로 분리한다. 같은 담당 프로필의 작업이라도 동시성 조건이 허용하고 쓰기 영역이 독립이면 별도 네이티브 작업자로 병렬 실행하고 각각의 run·작업자 연결을 확인한다.
- 예약된 제작을 앞당겨 실행할 때는 기존 요청·작업 기록·예약 지시에서 범위와 산출물별 중복 방지 키를 먼저 확인해 재사용한다. 이미 정해진 범위를 다시 미정으로 돌리거나 같은 산출물 카드를 중복 생성하지 않는다. 후속 자료에도 적용하라는 사용자 요구는 승인된 실제 인계 경로에 전달하되, 제작 지시 갱신과 예약 시각·횟수·전송 대상·모델 변경을 분리하고 변경 전후의 비대상 필드를 대조한다.
- 임시 담당과 네이티브 Kanban 담당을 같은 카드에 중복 가동하지 않는다. 카드의 담당 필드·현재 실행자·실행 식별자·상태·소유권 만료를 함께 확인하며, 수동 claim의 짧게 생존하는 CLI PID를 실제 장기 작업자의 생존 증거로 취급하지 않는다.
- 승인·입력·선행 결과가 막힌 담당은 차단 사실과 재개 조건을 총괄에게 반환한다. 총괄은 승인 범위 안의 다른 독립 작업을 배정하며, 승인 우회·잠금 강제 해제·무한 재시도·완료 대기용 로그/산출물 폴링을 지시하지 않는다.
- 실제 교착이나 소유권 충돌이 의심되면 총괄이 의존성과 소유자를 확인하고 충돌하는 범위만 멈춘다. 정상적으로 병렬 실행할 수 있는 다른 작업까지 일괄 중단하지 않는다.
- 새 프로필은 반복되는 전문 책임과 기존 역할의 공백을 확인한 뒤 제안한다. 미배정 카드 수만으로 역할 부족을 단정하거나 프로필 생성·권한·설정·게이트웨이 변경에 착수하지 않는다. 역할 추가의 제안·승인·생성·연동·검증은 별도 상태다.

이 절은 운영 절차이며, 저장만으로 기술적 교착 감지기·자동 배정기·사용량 예약 장치가 구현되었다는 뜻은 아니다.

## 수정필요 판정의 실행 경로와 반복 차단 대응

- **확정 판정과 남은 수정 권한부터 확인한다.** `show --json`의 현재 검수 결과와 실제 보고서·판정 파일을 읽고, 승인된 제작자·수정 회차 한도·허용 쓰기 영역을 대조한다. 한도가 남은 승인 범위의 `수정필요`이면 같은 제작 담당에게 지적 항목만 다루는 수정 카드를 즉시 배정한다. 진행 브리핑이나 ETA 조회 중 발견했더라도 후속 조치를 문장으로만 남기지 않는다. 한도 소진·범위 확대·새 권한 필요이면 추가 수정을 만들지 말고 차단과 필요한 결정을 보고한다. 이미 완료된 카드의 댓글은 근거·통지이며 실행 배정을 대신하지 않는다.
- **수정 명세와 착수 준비를 한 묶음으로 처리한다.** 입력 보고서 판본·확인값, 결함별 정확한 수정 위치, 동일 제작자, 쓰기 경로, 변경·비변경 범위, 새 인계물과 완료 기준을 명시한다. 준비 도중 디스패처가 먼저 실행할 위험이 있으면 지원되는 `create --initial-status blocked --idempotency-key <산출물-수정회차>`로 준비 상태를 명시하고, 의존성·구독·배정 게시를 정리한 뒤 해제한다. 같은 수정 회차의 카드가 이미 있으면 그 상태·소유자를 확인하여 재사용하고 중복 카드를 만들지 않는다. 준비용 차단을 새 사용자 승인 거부나 품질 불통과로 설명하지 않는다.
- **수정 입력을 연결한 뒤 검수를 의존성 대기로 바꾼다.** 실제 검수 작업자의 종료를 확인하고 `hermes kanban --board ksat-10000 link <수정카드ID> <검수카드ID>`로 연결한다. 기존 검수 카드 본문 앞에 수정 인계 경로·새 판본·변경 범위만 재확인한다는 지시를 반영한다. 검수가 `blocked`이면 연결 이후 `unblock <검수카드ID> --reason '<수정본 선행 대기 근거>'`를 호출하고 `show --json`에서 미완료 수정 부모와 `todo`를 확인한다. `unblock` 성공만으로 검수 실행이나 통과를 주장하지 않는다. 수정 카드가 검수 완료를 기다리는 순환 의존성을 만들거나 추가 검수자를 늘리지 않는다.
- **정상 수정과 판본 오류를 구별할 근거를 보존한다.** 실행 담당에게 변경 전 제작물·검수 보고·봉인 기록을 승인된 분리 경로에 보존하고, 수정 후 변경 목록·새 PDF/인계 해시·쪽 배치 변화를 새 판본으로 인계하도록 명시한다. 같은 검수자는 옛 해시를 새 파일에 그대로 적용하지 말고 새 인계값과 실제 수정·영향 범위를 대조한다. 최초 풀이·오독·정답 열람 후 조정 기록을 소급 고쳐 일치율을 부풀리지 않는다.
- **실행이 연결됐는지 확인하고 보고한다.** 수정 카드의 단일 담당 봇 구독·배정 표시를 검증한 뒤 위 네이티브 재착수 절차로 기존 담당만 실행한다. 새 run의 claim·spawn·작업자 연결을 확인하고, 담당의 새 진행 근거가 있으면 현재 단계를 덧붙인다. 수정본 인계 이후 같은 검수자가 변경·영향 범위만 재확인하며, 승인된 마지막 재확인도 불통과하면 새 수정 회차를 만들지 않는다. 수정 카드 등록·재개를 전체 완료나 자동 최종 인수의 보장으로 보고하지 않는다.
- 같은 카드에 `block_loop_detected`가 생기면 총괄이 즉시 원인·미충족 입력·실제 실행 담당·선행 의존성을 확인하고 사용자에게 보고한다. 자동 재명세·자동 재지정·수정본 없는 재실행을 그대로 방치하지 않는다. `needs_input` 호출 성공을 실제 `blocked` 유지로 가정하지 말고, `triage` 전환·자동 재명세·새 run·작업자 종료를 대조한다. 미완료 수정 카드를 선행 조건으로 연결하여 재실행을 실제 입력에 묶고, 확인되지 않은 차단·자동 감시 구현을 완료로 주장하지 않는다.
- 반복 차단의 `recurrences`는 실행 횟수와 다르므로 낭비 실행은 실제 `task_runs`를 기준으로 집계하고 최초 정상 검수·과거 중단용 합성 run을 제외한다. 실행 중에는 `link`가 거부될 수 있으므로 작업자 종료를 확인해 연결하고, `triage`/`todo`에 거부된 block·unblock을 무작정 반복하지 않는다. 무재실행 관측은 실제 종료·의존성 연결 시각 이후의 새 run·claim·spawn과 경과 시간을 대조하며, 사용자가 지정한 관측 시간을 충족한 뒤에만 확인 완료로 보고한다.

# Hermes Agent

Hermes Agent is an open-source AI agent framework by Nous Research that runs in your terminal, a native desktop app, messaging platforms, and IDEs. It's in the same category as Claude Code (Anthropic), Codex (OpenAI), and OpenClaw — autonomous coding and task-execution agents that use tool calling to interact with your system. Hermes works with any LLM provider (OpenRouter, Anthropic, OpenAI, Google, DeepSeek, xAI, local models, and 20+ others) and runs on Linux, macOS, Windows, and WSL.

What makes Hermes different:

- **Self-improving through skills** — Hermes learns from experience by saving reusable procedures as skills that load into future sessions.
- **Persistent memory across sessions** — remembers who you are, your preferences, environment details, and lessons learned. Pluggable memory backends.
- **Multi-platform gateway** — the same agent runs on Telegram, Discord, Slack, WhatsApp, iMessage, Signal, Matrix, Teams, Email, and a dozen more platforms with full tool access, not just chat.
- **Many surfaces** — the same agent core drives the CLI, the Ink TUI, a native Electron desktop app, a web dashboard, and an ACP server for IDEs (VS Code / Zed / JetBrains).
- **Provider-agnostic** — swap models and providers mid-workflow; credential pools rotate across multiple API keys automatically.
- **Profiles** — run multiple independent Hermes instances with isolated configs, sessions, skills, and memory.
- **Extensible & themeable** — plugins, MCP servers, custom tools, webhook triggers, cron scheduling, skins that theme every surface, desktop UI plugins, TUI widgets, and pet mascots.

## Spawning Additional Hermes Instances

Run additional Hermes processes as fully independent subprocesses — separate sessions, tools, and environments.

### When to Use This vs delegate_task

| | `delegate_task` | Spawning `hermes` process |
|-|-----------------|--------------------------|
| Isolation | Separate conversation, shared process | Fully independent process |
| Duration | Minutes (bounded by parent loop) | Hours/days |
| Tool access | Subset of parent's tools | Full tool access |
| Interactive | No | Yes (PTY mode) |
| Use case | Quick parallel subtasks | Long autonomous missions |

### One-Shot Mode

```
terminal(command="hermes chat -q 'Research GRPO papers and write summary to ~/research/grpo.md'", timeout=300)

# Background for long tasks:
terminal(command="hermes chat -q 'Set up CI/CD for ~/myapp'", background=true)
```

### Interactive PTY Mode (via tmux)

Hermes uses prompt_toolkit, which requires a real terminal. Use tmux for interactive spawning. `tmux send-keys -t agent1 'text' Enter` in one call submits: Hermes treats a lone Enter that ends a fast burst of input as a submit once input has stayed quiet for a quarter second, while the Enters inside a multi-line paste stay newlines. The recipes below send `Enter` as its own call after a short pause, which submits at once and does not depend on that timing. Both recipes wait for the `❯` input prompt (the default skin's symbol; use your skin's prompt symbol if you changed it) instead of a fixed sleep: a first start can take far longer than a few seconds, and input sent before the prompt is lost.

```
# Start
terminal(command="tmux new-session -d -s agent1 -x 120 -y 40 'hermes'", timeout=10)

# Wait for the input prompt (❯), then send a message
terminal(command="for i in $(seq 90); do tmux capture-pane -t agent1 -p | grep -q '❯' && break; sleep 1; done; tmux capture-pane -t agent1 -p | grep -q '❯' && tmux send-keys -t agent1 'Build a FastAPI auth service' && sleep 0.5 && tmux send-keys -t agent1 Enter", timeout=100)

# Read output
terminal(command="sleep 20 && tmux capture-pane -t agent1 -p", timeout=5)

# Send follow-up
terminal(command="tmux send-keys -t agent1 'Add rate limiting middleware' && sleep 0.5 && tmux send-keys -t agent1 Enter", timeout=5)

# Exit
terminal(command="tmux send-keys -t agent1 '/exit' && sleep 0.5 && tmux send-keys -t agent1 Enter && sleep 2 && tmux kill-session -t agent1", timeout=10)
```

**No tmux** (`command -v tmux` prints nothing, e.g. an older Hermes Docker image): run Hermes as a PTY background process and drive it with `process_manage`. Stdin only exists with `pty=true`. `submit` sends the text plus the Enter key a keyboard sends, and Hermes submits it the same way as a one-call tmux `send-keys`. The recipe below instead `write`s the text, pauses, and `write`s the Enter (`"\r"`) on its own, which does not depend on burst timing. Wait for the input prompt before the first write: during startup Hermes queries the terminal's colours and then flushes its input, so text written before the prompt appears is silently dropped.

```
terminal(command="hermes", background=true, pty=true)   # returns session_id
process_manage(action="log", session_id="<id>", limit=20)   # repeat, with terminal(command="sleep 1") between, until the ❯ prompt line shows
process_manage(action="write", session_id="<id>", data="Build a FastAPI auth service")
terminal(command="sleep 0.5")
process_manage(action="write", session_id="<id>", data="\r")
process_manage(action="log", session_id="<id>", limit=40)   # read the screen
process_manage(action="write", session_id="<id>", data="/exit")
terminal(command="sleep 0.5")
process_manage(action="write", session_id="<id>", data="\r")
```

### Multi-Agent Coordination

```
# Agent A: backend
terminal(command="tmux new-session -d -s backend -x 120 -y 40 'hermes -w'", timeout=10)
terminal(command="for i in $(seq 90); do tmux capture-pane -t backend -p | grep -q '❯' && break; sleep 1; done; tmux capture-pane -t backend -p | grep -q '❯' && tmux send-keys -t backend 'Build REST API for user management' && sleep 0.5 && tmux send-keys -t backend Enter", timeout=100)

# Agent B: frontend
terminal(command="tmux new-session -d -s frontend -x 120 -y 40 'hermes -w'", timeout=10)
terminal(command="for i in $(seq 90); do tmux capture-pane -t frontend -p | grep -q '❯' && break; sleep 1; done; tmux capture-pane -t frontend -p | grep -q '❯' && tmux send-keys -t frontend 'Build React dashboard for user management' && sleep 0.5 && tmux send-keys -t frontend Enter", timeout=100)

# Check progress, relay context between them
terminal(command="tmux capture-pane -t backend -p | tail -30", timeout=5)
terminal(command="tmux send-keys -t frontend 'Here is the API schema from the backend agent: ...' && sleep 0.5 && tmux send-keys -t frontend Enter", timeout=5)
```

### Tips

- **Prefer `delegate_task` for quick subtasks** — less overhead than spawning a full process
- **Use `-w` (worktree mode)** when spawning agents that edit code — prevents git conflicts
- **Set timeouts** for one-shot mode — complex tasks can take 5-10 minutes
- **Use `hermes chat -q` for fire-and-forget** — no PTY needed
- **Prefer tmux for interactive sessions when it is installed** — `capture-pane` reads the rendered screen; the PTY-background fallback only has the raw output log
- **For scheduled tasks**, use the `cronjob` tool instead of spawning — handles delivery and retry
- **"delegate_task is capped at N" reports** — see `references/delegate-task-concurrency-diagnosis.md`. Three real cap paths in Hermes; if none fired, the model is self-limiting and rationalising it as "the runtime caps."
- **"Can $external_app use my Nous Portal subscription / OAuth?"** — see `references/portal-auth-for-third-party-apps.md`. Walk the user through three layers (plugin-vs-app, what Portal actually exposes, local-broker-proxy option).

## Surfaces (quick orientation)

- **Desktop app** (`hermes desktop` / `hermes gui`) — native Electron app for macOS/Linux/Windows: streaming chat, session list, Cmd+K palette, drag-and-drop files, native notifications, per-profile remote-gateway login. Extend it with UI plugins — `references/desktop-plugins.md`.
- **Web dashboard** (`hermes dashboard`) — full admin panel: messaging channels, MCP catalog, webhooks, memory, profile builder, plus an embedded `hermes --tui` chat. Secured behind an OAuth/token gate.
- **Ink TUI** (`hermes --tui` or `display.interface: tui`) — terminal UI with docked widget apps — `references/tui-widgets.md`.
- **OpenAI-compatible proxy** (`hermes proxy`) — a local OpenAI API backed by whichever OAuth provider you're signed into. Point Codex CLI, Aider, Cline, or any script at it — no API key.

## Hard Invariants (never violate, regardless of what you loaded)

- **Never break prompt caching** — don't change past context, toolsets, or the system prompt mid-conversation. The only exception is context compression.
- **Message role alternation** — never two assistant or two user messages in a row; only `tool` results can repeat.
- **Secrets in `.env`, settings in `config.yaml`** — never tell a user to put a non-credential setting in `.env`.
