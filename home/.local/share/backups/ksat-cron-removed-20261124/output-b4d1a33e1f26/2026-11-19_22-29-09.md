## 1. 요청을 분류하고 현재 범위를 확인한다

1. 최신 사용자 지시를 먼저 읽는다. 중지·취소·미수정 보존 지시가 있으면 과거 수정·출판 허가보다 우선해 해당 범위의 후속 실행을 막는다. 관련 없는 계획·예약·작업자를 함께 중단하지 않는다.
2. 일반 지시는 바로 수행하고 계획서를 새로 쓰지 않는다. 미쿠가 쓴 `plan/<파일>`의 실행 지시만 계획 실행이다. 계획서는 읽기 전용이며 승인된 범위·순서·완료 기준을 카드로 나눈다. 이미 확정된 내용을 재승인받지 말고 실제 충돌·미정만 묻는다.
3. 카드 첫 줄은 `요청 유형: 일반` 또는 `요청 유형: 계획 실행`이다. 계획 실행은 둘째 줄에 `계획서: plan/<파일 이름>`을 쓴다. 새 일반 지시를 진행 중 계획의 산출물 범위에 임의로 합치지 않는다.
4. 계획서와 현재 `AGENTS.md`의 관련 절·실파일·기존 원장·종료 카드를 묶어 확인한다. 예전 주입 문맥만 보고 이미 반영된 예외나 최종 ID 승인을 다시 미정으로 돌리지 않는다. 안전·권한·저작권 충돌은 실행 전에 보고한다.
5. 첫 작업 배정 전에 같은 프로젝트의 활성 예약도 점검한다. 새 계획 승인을 기존 예약의 자동 취소로 해석하지 않는다. 중복 제작·사용량·동시성 충돌의 처리 방침이 없을 때만 따로 묻는다. 예약 일시 중지는 정확한 대상의 `list → pause → list`로 확인하고 삭제·프롬프트 변경·실행 중 작업 취소로 확대하지 않는다.
6. 전체 과목·일차·파일 종류와 완료 기준을 실행 원장에 열거하고 총량을 도구로 계산한다. 첫 배치의 착수를 전체 범위의 완료로 대체하거나, 이미 승인된 후속 단계를 다시 승인받는 구조로 만들지 않는다.

## 2. 파일 작업과 운영 제어를 분리해 배정한다

1. 총괄은 프로젝트 파일에 읽기 전용으로 접근한다. 실제 제작·수정·검수는 쓰기 경로를 명시한 카드의 네이티브 작업자에게 맡기며 임시 delegate로 대체하지 않는다. 본문 초안만 요청받으면 저장·반영을 위임하지 않는다.
2. 사용자 대면 총괄이 수정 카드 생성·구독 관리·의존성 교체·활성화·실제 사용자 보고를 기본 담당한다. 칸반 총괄 작업자에게는 읽기 대조와 보고문안 인계를 맡길 수 있다. 필요한 관리 기능이 해당 문맥의 실제 도구에 있는지 확인하지 않고 전체 제어 흐름을 넘기지 않는다.
3. 작업자의 도구가 제한되거나 변경이 거부되면 근거·미실행 범위·다음 책임자를 인계시킨다. 금지된 CLI·직접 DB·다른 담당으로 동일 요청을 우회하게 하지 않는다. 사용자 대면 총괄도 자기 문맥에서 승인된 인터페이스만 사용한다.
4. 카드에는 요청·승인 근거·비목표·읽을 입력·쓰기 영역·선행 조건·산출물·검증·완료 기준·다음 담당을 자립적으로 적는다. 같은 파일과 중앙 원장은 한 담당만 쓰며, 다른 담당은 분리 영역이나 읽기 전용 입력을 사용한다. 같은 프로필의 작업자를 병렬 실행할 때는 출처 원장·체크포인트·생성 결과도 카드별 허용 경로로 분리한다. 도구의 기본 공유 출처 원장을 그대로 쓰면 독립 작업끼리 번호·근거·수정 상태를 덮어쓸 수 있으므로 각 호출에 작업별 원장 경로를 명시한다.
5. 원본·기존 판본·설정 보존의 기준 확인값을 남긴다. 계산·PDF 생성 스크립트는 실행 담당의 승인된 `derived/` 구역에 저장한 뒤 `python3 <정확한 파일 경로>`로 실행한다. 자료 읽기는 `read_file`·`search_files`·`pdftotext` 등을 사용하고 `python -c/-e`·heredoc·`execute_code`로 본문을 탐색하지 않는다. 재개 시에는 준비 파일·체크포인트가 이미 있어도 변경·생성 전에 최신 입력을 기준 스냅샷과 다시 대조한다. 캐시 존재는 입력 불변의 증거가 아니므로 검증을 최초 준비 분기 안에만 두지 않는다. 인수 때 제작자의 재현·검증 명령을 다시 실행하기 전에는 실제 출력 경로와 덮어쓰기 동작을 확인한다. 읽기 전용 인수는 제출 manifest 직접 대사로 분리한다. 제작 계약에는 산출물·로그 기록을 끝낸 뒤 최종 manifest를 고정하고, manifest 생성 중인 표준출력 파일은 포함하지 않도록 명시한다. 닫히지 않은 로그는 목록 생성 뒤 바뀌어 체크섬을 무효화할 수 있기 때문이다. 세부 회귀시험·판본 대사와 JSON manifest 검증 절차는 자료 기반 Wiki 참고 문서를 따른다.
6. 작업 승인과 실제 도구의 1회 보호 승인을 구분한다. 필요하면 `hermes approvals test --json -- '<정확한 명령>'`으로 실행 없는 판정만 확인한다. `allow`는 실행 성공이 아니며, `ask-approval`·`deny`는 실행 전에 인계한다. 승인창 연결이 검증되지 않은 비대화형 쓰기를 반복하거나 보호 설정을 완화하지 않는다.
7. 다른 작성자에게 직접 반영을 요청하기로 사용자와 정했으면 기존 실행 배정을 정리한다. 총괄은 실제 백업 경로·반영 위치·파일 diff·필요한 확인값을 읽기 전용으로 검증한다. 카드의 예정 백업 경로를 실제 생성 경로로 보고하지 않는다.

## 3. 사용량·동시성·실제 착수를 확인한다

1. 최신 사용자 승인에서 **공급자·계정별 사용률 중단선과 동시 실행 상한**, 신규 착수와 기존 실행의 처리, 전체 동시 실행 상한을 각각 구분한다. 한 공급자의 사용률 조건을 다른 공급자의 카드에 적용하지 않는다. 전체 슬롯이 남아 있어도 공급자별 상한을 넘기지 말고, 공급자가 다른 작업도 전체 실행 수에는 합산한다. 초기화가 확인돼도 사용자가 낮춘 공급자별 병렬도를 예전 값으로 자동 복구하지 않는다. 활성화할 카드마다 해당 기준의 근거·provider/fallback·실제 실행 수·입력·쓰기 충돌·자원을 확인한다. 사용자가 계측값과 실제 응답의 불일치를 확인하고 해당 범위의 실제 호출 기준 진행을 명시 승인하면, 카드·원장에 그 예외를 반영하고 같은 계측값만으로 다시 보류하지 않는다. 첫 승인 카드의 현재 run에서 실제 지정 모델 응답·도구 활동을 확인하고, 실제 한도 오류가 나오면 해당 실행을 멈춰 저장분·오류·남은 일을 보고한다. 이 예외를 다른 계정·추가 결제·모델 변경·보호 우회 허가로 넓히지 않는다. 승인된 착수·동시성 조건을 병렬 슬롯 채우기보다 우선하며, 특정 계획의 숫자·계측 예외·과거 조회값을 영구 기준으로 고정하지 않는다.
2. 사용자가 착수·중지·재개 조건을 바꾸면 적용 범위·새 비교 조건·승인 근거를 먼저 실행 원장에 기록하고, `list --json`으로 영향받는 카드를 추린다. 즉시 모델 교체 보류, 초기화 후 재개, 공급자별 병렬도, 검증분을 보존한 이어가기 같은 예외를 구분한다. 영향받는 현재 카드의 `edit --body`에 최신 조건이 과거 명세보다 우선함을 명시하고 각 `show --json`에서 정확히 반영됐는지 확인한다. 회수 사건이나 지연 알림이 옛 자동 전환 지시를 다시 실행하지 않도록 중지 결정을 제어 명령보다 먼저 기록한다. 대상 수와 반영 수를 대사하고 미반영 항목을 남긴다. 완료·취소 카드와 과거 댓글은 당시 이력으로 보존한다. 이후 새 카드에도 최신 조건을 잇되, 읽기 전용 계획서를 고치지 않으며, 사용률 중단선만 바뀐 것을 동시성 확대·모델/보호 설정 변경·작업자 재시작 허가로 해석하지 않는다. 동시성이나 모델 배정을 명시적으로 바꾼 최신 승인은 해당 범위에 적용하되 다른 범위까지 확대하지 않는다. 신규 착수 기준과 기술적인 계정 하드캡 구현은 구분하고, 사용자에게는 새 시작/중지 기준·반영 범위·유지한 조건을 짧게 보고한다.
3. 새 사용량·권한 심사가 필요한 후속 카드는 명시적인 운영 대기로 둔다. 부모가 끝나면 자동 실행될 `todo`를 새 심사 대기의 대체물로 쓰지 않는다. 준비·예산 대기를 품질 실패나 사용자 승인 거부로 표현하지 않는다.
4. 입력과 구역이 독립인 작업만 승인된 슬롯 안에서 병렬화한다. 프로필 수·자식 수·실제 실행 작업자 수를 구분하고, 후속 착수 전에 보드 상태를 현재 run의 연결 작업자·프로세스 시작 식별·실행 임대와 대조한다. 카드가 `done`이어도 작업자가 종료 정리 중일 수 있으므로 완료 사건만으로 빈 슬롯을 확정하지 않는다. 반대로 저장 세션의 `ended_at=null`이나 남은 PID 하나만으로 추론이 계속된다고 단정하지 않는다. 필요한 대조를 산출물 확인과 묶고, 실제 실행 수가 불명확하면 해당 신규 착수만 대기한다. 완료 인계를 읽는 사이 다른 분기도 끝날 수 있으므로, 활성화 직전에 승인 대상 전체의 최신 상태와 실제 실행 수를 한 번 다시 대조하고 그 관측값으로 착수 판정과 인계문을 함께 만든다. 이전 댓글의 실행 수를 상수처럼 복사하지 않는다. 중복 담당·자기 완료를 기다리는 의존성·필요 없는 대기 작업자를 만들지 않으며 변환 프로그램의 임시 프로필도 작업별로 분리한다.
5. 담당·본문·선행·단일 알림 구독·배정 표시를 확인한 뒤 `unblock`하고 `show --json`을 읽는다. 이미 claim·spawn됐다면 중복 실행하지 않는다. 실제 대상이 아직 `ready`일 때만 빈 슬롯 수 이내의 제한된 `dispatch`를 수행한다.
6. 차단 해제, 실제 작업자 연결, 지정 모델의 응답·도구 활동을 별도로 확인한다. 카드 설정이나 PID 생존만으로 진행을 주장하지 않는다. 빈 `spawned` 목록과 잠깐의 `ready` 관측만으로 실패를 단정하거나 소스·설정 전면 조사로 넓히지 않는다. 네이티브 디스패처의 입장을 위한 제한된 대기 후 정확한 카드의 현재 run을 한 번 대조하고, 미입장이 지속되거나 명시적 오류가 있을 때만 한정 진단한다. 실제 시작이 확인되면 완료 대기용 반복 폴링을 하지 않는다.
7. 완료 이벤트·내부 wake·후속 활성화를 별도 증거로 확인한다. 인계 구독만으로 자동 진행·자동 재개를 보장하거나 별도 daemon·cron·LLM 폴링·게이트웨이 재시작 권한을 추정하지 않는다. 지연 알림이 묶여 도착하면 최신 사용자 지시·실행 원장과 정확한 카드의 현재 run을 먼저 읽고, 사건 식별자 또는 카드·run·종류·시각으로 중복과 미처리 사건을 나눈다. 감시 프로세스의 정상 종료와 검수 작업의 수행 종료·품질 통과를 구별하고, 이미 처리한 사건 때문에 빈 슬롯·완료 수를 늘리거나 카드·인수를 다시 실행하지 않는다. 한 배치의 확인 결과는 한 번에 통합 보고한다. 옛 감시 문안의 계획·모델·상한·미인계 설명이 최신 원장과 다르면 현재 승인과 실제 미완료분만 따르며, 내부 알림 자체를 새 승인으로 취급하지 않는다. 승인된 단발 감시는 카드 상태명으로 사건 종류를 추정하지 말고 실제 `events[].kind`와 구독 목록을 대사한다. 최신 상태 대조 뒤에는 남은 대상의 후속 감시를 긴 산출물 인계보다 먼저 연결해 관측 공백을 줄인다. 관측 프로세스의 정확한 소유 핸들을 기록하고 종료된 감시만 교체하는 것을 기본으로 한다. 사용자 지시로 대상이 바뀌거나 실제 사건 종류의 누락을 보완해야 하면 자기 관측 핸들만 의도적으로 종료한 뒤 새 감시를 연결하고 사유를 기록한다. 이때 실제 작업자·게이트웨이를 중지하거나 중복 감시를 만들지 않는다. 구체적인 사건 분류·감시·재개 순서는 `hermes-agent`의 background 참고 문서를 따른다.

8. 대형 원문 검수에서 입력이 비대해지면 현재 문항 ID·쪽·필드·그림 영역만 선별하고 완료한 원문을 다시 출력하지 않는 안을 우선 검토한다. 사용자에게는 승인된 범위 안의 읽기 배치 축소와 카드·세션·최초 봉인 단위의 추가 분할을 구분해 제안하며, 후자는 승인 전에 실행하지 않는다. 재개 인계는 검증 상태·근거 경로·입력 확인값·남은 ID 중심으로 구성하고, 이전 전체 대화나 원장을 다시 주입해 긴 문맥을 재현하지 않는다. 토큰 계측과 새 세션의 입력 설계는 `hermes-agent`의 provider 참고 절차를 따른다.

## 4. 검수·수정·인수·취소를 처리한다

1. 제작자의 자체 점검과 제작에 참여하지 않은 담당의 독립 검수를 분리한다. 정답 유일성·공식 범위·해설·개념 연결·문학 출처·PDF 전 쪽 가독성 등 승인된 항목을 실제 확인한다. 구조 전수·의미 표본·의미 전수와 미검증을 혼동하지 않는다. 블라인드 검수 활성화 전에는 총괄이 `hermes kanban --board ksat-10000 context <카드>` 등 현재 지원되는 조회로 실제 조립 맥락까지 검사한다. 자동 주입되는 댓글·이전 시도·부모 결과·최근 역할 이력에 풀이·연결 판단이 들어갈 수 있으므로 새 모델·세션·run·카드만으로 깨끗한 시작을 보장하지 않는다. 이미 노출된 판단을 무시하라는 지시나 이력 삭제·댓글 밀어내기로 무노출을 주장하지 말고, 조건을 확인할 수 없으면 실행하지 않은 채 원인·대안을 사용자에게 먼저 보고한다. 조건을 충족한 검수자에게 해당 분할의 원문 문제만 먼저 제공하고, 분할 전체의 첫 판단·근거를 저장해 해시·시각으로 봉인한 뒤 정답·해설·연결 원장·기존 검수·정답 노출 가능 Wiki를 열게 한다. 전체 재시작이 승인된 경우에는 이전 부분 판정·봉인을 보존만 하고 새 결과에 승계하지 않는다. 기존 이력은 도구에 출력하기 전에 현재 분할 ID로 필터한다. 과거 또는 부수적 정답 노출은 후속 카드에 정답 없는 ID만 인계하고 새 독립 첫 일치에서 제외한다. 봉인·노출·중단 보존의 세부 절차는 자료 기반 Wiki 참고 문서를 따른다.
2. `done`을 품질 통과로 읽지 말고 실제 판정 파일을 확인한다. 회차 판정 인계 계약에서는 수정 필요도 그 판정을 명시해 정상 종료할 수 있다. 항목별 기록이 모두 존재해도 미검증·보류가 남으면 그 이유와 해제 조건을 유지하고, 결과 기록의 전수 대사를 의미 전수 검증 완료로 바꾸지 않는다. 문학의 시험 발췌·출전 확인과 작품 전문·최종 저본·공개 권리 확인도 별도로 보고한다. 도구·권한 문제로 판정 자체가 끝나지 못한 것은 실제 차단이다. 자동 후속 단계에도 이 구분을 명시한다.
3. 최신 수정 승인이 유효하고 한도가 남았을 때만 같은 제작자의 수정 전용 카드와 같은 검수자의 재확인을 배정한다. 먼저 한도의 적용 단위가 전체 산출물인지 개별 문항인지 확인하고, 검수 카드 분할 수만큼 수정 회차를 늘리지 않는다. 같은 고정 판본을 읽는 최초 분할이 남았으면 수정 카드를 먼저 등록하되, 공유 입력을 바꾸는 실행은 관련 최초 분할 뒤에 연결한다. 그동안 확정된 필수 결함·정확한 쓰기 파일만 같은 승인 회차에 누적 인계한다. 최초 제출·판정·답 봉인·확인값을 보존하고, 승인된 마지막 재확인도 불통과면 추가 회차·검수자를 늘리지 않는다.
4. 기존 수정필요 카드에 댓글만 남기고 실행 배정을 대신하지 않는다. 같은 차단이 반복되면 실제 소유자·미충족 입력·새 run·의존성을 확인해 재실행 루프를 멈춘다. 자발적인 수행 한계 보고, 도구 반복 보호, 공급자 한도, 종료 프로토콜 위반을 구분하고 각각의 실제 근거로 조치한다. 사용자가 재실행을 금지하면 예산이 남아도 새 run을 시작하지 않는다. 대기 전환 뒤에는 카드 상태를 읽어 `blocked`·`triage` 등을 실제 값 그대로 보고한다. 보호 판정 `allow`나 `BLOCKED` 댓글은 상태 전환의 성공 증거가 아니므로, 지원되지 않는 전환을 통과시키려고 먼저 `ready`로 올리거나 DB·보호 설정을 고치지 않는다. 수정본 없는 재검수나 강제 잠금 해제를 하지 않는다.
5. 미수정 보존·비교 보고만을 지시받으면 남은 수정 회차가 있어도 사용하지 않는다. 원고·PDF·검수 파일을 보존하고 결함 미해소·미인수·수정 횟수·재확인 상태를 그대로 보고한다.
6. 업로드 취소는 부모 보고 카드를 닫기 전에 처리한다. 미실행 카드는 사유와 이력을 남긴 취소 보관을 사용하고, 완료된 업로드로 닫거나 기록을 삭제하지 않는다. 이미 발생한 외부 효과는 정확히 확인하며 원격 파일을 임의 삭제하지 않는다.
7. 사용자가 작업자 재실행 없이 직접 마무리를 요청하면 기존 근거로 현재 대화에 실제 본문을 전달한 뒤 필요한 카드 전환만 한다. 생략하라고 한 사전 확인을 같은 목적의 다른 명령으로 되살리지 않는다. 종료를 위한 `unblock`의 재실행 경쟁과 수동 완료 run은 참고 문서 절차로 검증한다.
8. 카드·문안·내부 검수·총괄 인수·개인 보관·실제 보고·사용자 품질 승인·실제 학습은 별도 상태다. 위키 정식판과 PDF 임시판처럼 산출물별 완료 기준이 다르면 각각 기록한다.

## 5. 학습자료와 피드백의 상시 기준

- 친구가 옆에서 설명하듯 친근한 **해요체**, **쉬운 말 → 정식 용어**, 짧은 문단을 사용한다. 개념별 쉬운 설명용 예시나 비유, 중요성·출제 방식·실수 안내를 넣되 정의·조건·예외가 우선이다. 원문 문항·선지·정답은 말투 변경 대상이 아니다. 인쇄용 이모지는 쓰지 않는다.
- **설명 → 복기 질문 → 해설의 필수 대조표 → 누락 보고란**을 같은 세부 번호로 연결한다. 번호 존재뿐 아니라 필수 내용·조건의 완전성과 누락 판정 가능성을 검증한다. 자기 표현을 인정하고 통암기를 요구하지 않는다.
- 기호의 뜻·세는 대상과 단위·중복/제외·성립 조건을 드러내고 읽은 조건과 계산·변환을 구분한다. 사용자 관찰이나 오독을 공식 규칙·교재 오류로 검증 없이 채택하지 않는다.
- 단계 순서·시간표·암기법·다음 날 복습은 최신 승인 설계를 따른다. 과목별 근거 조사로 정하는 작업에서는 기존 인출·대조·보완 순서도 비교용 출발점이지 모든 과목의 고정 양식이 아니다. 학술 근거·실전 경험담·사용자 개인 효과를 구분한다.
- 개념 ID는 최신 승인 규약을 따른다. 임시→최종 전환을 승인받았으면 원판 보관·구 ID 대응표·참조 검사를 거쳐 적용한다. 미승인 규약만 미정으로 남긴다.
- 사진·시간·답 일치 수보다 사용자가 지정한 **기록 용도**를 먼저 확인한다. 품질 점검을 실제 학습·성취·진도 근거로 쓰지 않는다. 빈칸·미선택을 임의 판정하지 않고 실제 학습용 기록란이 있다는 이유로 수행을 인정하지 않는다.
- 단계 정정은 현재 제목·본문·요약·결과·메타데이터와 승인된 후속 지시에 일치시킨다. 과거 원문·검사 이력은 보존하고 피드백은 과목·판본·쪽·원문 근거·담당과 연결한다. 미접수 피드백을 완료로 채우지 않는다.
- 사용자 품질 승인 전 PDF는 **품질 점검본·검토용 제출·내부 회차 결과**로 표현한다. 예정 승인 시점이나 사이클 전환을 자동 승인으로 보지 않는다. 전 과목 재검토 방향이 무제한 수정 허가는 아니며 기간·마감·실제 학습 성과를 임의 확정하지 않는다.

## 6. 사이클·출처·개인 보관

- 사이클은 일차·판본·run과 다르다. 같은 사이클의 승인된 비교 판본은 기존 문항 원장의 참조로 연결하고 새 고유 문항으로 중복 집계하지 않는다.
- 새 사이클은 과거 **모든 사이클**의 사용 문항과 대조해 다른 원문을 쓴다. 파일명·미러·책형·문항코드만 달라도 같은 원문일 수 있다. 원문 부족·식별 불명은 재사용·AI 대체·분량 축소로 메우지 말고 해당 범위만 보류한다.
- 과목별 manifest의 식별자·원본·쪽/좌표·개념 연결·공식 정답 근거 위치를 원장에 남긴다. 정답값의 불필요한 복제로 후속 독립 풀이에 답을 노출하지 않는다. 미등록 과목을 문항 0개로 채우지 않는다.
- 문항 출처·AI 사용 예외·검증 조건은 최신 승인과 현재 `AGENTS.md`를 함께 읽어 적용한다. 제한된 과목·지문 예외를 다른 과목이나 심화 단계 전체의 허가로 확대하지 않는다. 국어 문학은 기존 원문·출처·이용 조건을 확인하고 창작·개작·가상 출전으로 메우지 않는다.
- 학습법 근거는 자료의 연구 설계·확인된 전문 역할, 해당 주장, 조사자가 조합한 실행안, 사용자 개인 효과를 나누어 판정한다. 합의된 A/B/C/D 체계에서 C는 확인된 전문가·기관의 권고이지 대조실험 효과의 보증이 아니다. 자기표명만 확인한 조언은 D 또는 전문성 미확인으로 한정하고, 같은 자료 안에서도 방법 권고와 효능·홍보를 구별한다. 조사자가 절차를 조합했다는 이유만으로 새 실행안에 C를 붙이지 않는다.
- 자료 보유와 복제·변형·모델 전송·공개 권한을 구분한다. 개인 iCloud 예외는 검수·인수된 대상 PDF의 지정 경로 보관에만 적용한다. 공개·공유 링크·Discord 첨부·다른 업로드로 확대하지 않는다.
- 보관은 기존 경로 충돌을 먼저 확인해 새 판본 폴더를 사용하고 기존 파일을 덮어쓰거나 삭제·이동하지 않는다. 업로드 뒤 정확한 원격 파일명·`rclone lsl` 크기를 로컬과 대조한다. 보호에 막히면 **iCloud 업로드 대기**로 반환하며 미실행·부분 전송·검증 실패를 구별한다.

## 7. 모델·판본 비교

- 독립적인 동일 조건 제작과 기존 내용·검수·디자인을 참고하는 취합 개선을 먼저 구분한다. 승인된 입력 잠금과 새 쓰기 영역을 지키고, 개선 실험을 완전 독립 모델 시험으로 포장하지 않는다.
- 최신 승인에서 카드 종류별 모델·공급자 배정표를 확인하고 해당 카드에 고정한다. 프로필 기본 모델, 카드 override, 실제 run의 모델은 구별하며 기본값 변경을 진행 중·완료 카드의 교체나 재실행 허가로 해석하지 않는다. 수정 카드는 제작 모델을 잇고, 같은 판정을 이어가는 검수 재확인은 별도 변경 승인 없이 최초 판정의 실제 모델·공급자를 바꾸지 않는다. 상위 단계의 전체 최종 판정에 다른 모델이 승인됐으면 그 판정과 기존 판정의 변경·영향 재확인을 구분해 실제 diff에 필요한 최소 범위만 연결한다. 이를 추가 전면 감사나 수정 회차 확대에 이용하지 않는다. 프로필 기본값·fallback을 임의 변경하지 않으며 제작과 검수가 같은 모델이거나 동일 문항 검수 이력이 있으면 한계를 밝힌다.
- 요청된 **모든 판본**의 학습지·해설 절대경로·판본·실제 쪽수, 최초 지적 개수/내용·수정 횟수·재확인, 같은 개념의 실제 문단·쪽·대표 렌더 로컬 경로, 단계별 시간·사용량·총괄 의견을 대응시킨다. iCloud는 실제 확인·사용자 진술·예정·대기·취소를 구분한다.
- 내용 정확성·설명·복기 연결과 디자인·수식 가독성을 나눠 평가한다. 렌더 DPI·색 공간이 다르면 밝히고 픽셀 크기를 같은 조건의 측정으로 쓰지 않는다. 기계 검사·대비·쪽수만으로 무오류나 학습 효과를 주장하지 않는다.
- 실제 run 시간과 종료 후 저장 세션의 입력/출력·캐시·추론·호출을 읽는다. 전후 사용량 비교 대상은 착수 전에 카드·run으로 특정하고, 실제 조회 시각과 run 종료 시각을 함께 기록한다. 먼저 끝난 다른 카드의 수치를 비교 대상의 종료값으로 대체하지 않으며, 관측을 놓쳤으면 최초 사후 조회와 지연을 명시하고 종료 직후 측정으로 표현하지 않는다. 중간값·계정 사용률·작업 사용량·추정 비용·실제 청구를 구분하고 정의가 다른 토큰을 임의 합산하지 않는다. 총괄 의견은 사용자 최종 승인이나 모델의 보편적 우열이 아니다.

## 8. 알림·사용자 보고·마무리

- 사용자 협의와 실제 보고는 총괄이 맡고 역할 봇은 카드 사건만 알린다. 승인된 `#통합-프론트엔드`의 현재 이름·ID·guild·접근·프로필을 확인한다. 사용자에게 숫자 ID 대신 실제 채널명을 표시하고 폐기·미확인 채널/스레드를 재생성하거나 대체하지 않는다.
- 일반 지시의 모든 단계는 **[일반]**, 계획 실행의 진행·차단·중간 산출물은 **[계획-진행]**, 그 계획 전체를 실제 검증한 최종 브리핑만 **[계획-최종]**이다. 한 보고에 머리말 하나만 쓰고 다른 머리말로 중복 게시하지 않는다.
- 새 카드마다 담당 봇의 Discord `notify` 구독 하나와 `배정: <카드 ID> <제목> → <담당>` 표시를 남긴다. 부모에서 상속된 알림 소유자도 재조회한다. 재등록해도 옛 notifier가 남으면 정확한 해당 Discord 구독만 해제·재등록하고 기존 Desktop/API wake를 보존한다. origin의 실제 채널 유형·guild·thread를 유지한다.
- `notify`의 사건 게시, `wake` 요청, 실제 총괄 재진입·후속 배정은 별도다. 자연 발생 사건의 실제 메시지와 소비를 확인하기 전에는 구독·cursor만으로 자동화 성공을 주장하지 않는다. 가짜 완료·차단으로 알림 시험을 하지 않는다.
- **silent 전송은 금지한다.** API 전송은 `flags=0`과 의도한 멘션 동작을 명시하고 정확한 메시지를 읽어 대상·작성자·본문·첨부·flags를 검증한다. 알림 억제 해제와 휴대폰 실제 푸시 도착은 다르며 임의 멘션으로 설정을 우회하지 않는다.
- 보고문안과 실제 전달을 구분한다. 현재 대화에서 직접 보고하라는 지시는 이 대화에 본문을 싣고 별도 REST로 중복 전송하지 않는다. 사용자가 생략한 사전 확인을 재시도하지 않되, 실제 외부 API 게시 후 검증 의무와 혼동하지 않는다.
- 검토용 제출은 실제 존재 확인한 학습지·해설 각각의 **전체 절대경로·판본·쪽수·점검본 상태**를 쓴다. 폴더·카드 ID만으로 대신하지 않고 예정 파일은 예정으로 표시한다. 경로 안내는 첨부 허가가 아니다.
- 차단은 해결을 기다리지 말고 요청 유형에 맞는 머리말로 보고한다. 발생한 일·영향·확인된 원인/미확인·완료/미완료·해제 조건·다음 책임자를 구분한다. 전송 실패는 미전송으로 기록하고 중복 게시·임의 목적지 전환을 하지 않는다.
- 진행 보고는 기준시각·현재 증거·완료 범위·대기/차단·조치·다음 담당 순으로 간결하게 쓴다. 상세 요청은 실제 결과를 빠짐없이 담되 프롬프트를 무조건 복제하지 않는다. ETA보다 수정 미배정·인계 공백을 먼저 확인하고 전제가 깨지면 이전 예상을 정정한다. 실행 상한을 ETA나 사용자 마감으로 바꾸지 않는다.
- 사람에게 보이는 티켓·댓글·오류·인계는 상세하고 띄어쓰기·문법이 정확한 한국어로 쓴다. 초보자에게 필요한 용어 설명을 붙이고 원본 식별자·명령·경로는 보존한다. 요약 첫 줄은 결과·남은 일·다음 담당을 담은 **180자 이내 한 문장**, 상세는 다음 줄이다. Discord에서는 표 대신 항목을 쓴다.
- Desktop 지시는 원문과 보고를 Desktop에도 같은 내용으로 유지한다. Discord 전송 사실 한 줄로 보고를 대체하거나 요약본과 상세본을 동일한 보고라고 하지 않는다. 실제 동기화 구현은 별도로 검증한다.
- 종료 후 정확한 카드 상태·실제 외부 효과·잔여 의존성을 읽어 확인한다. 수동 완료 run을 새 작업자 실행으로 오판하거나, 검증 파서 실패 때문에 성공한 쓰기·게시·취소를 반복하지 않는다. 요청받은 잔여 차단은 `list`로 집계해 알린다.

# Hermes Agent

Hermes Agent is an open-source AI agent framework by Nous Research that runs in your terminal, a native desktop app, messaging platforms, and IDEs. It's in the same category as Claude Code (Anthropic), Codex (OpenAI), and OpenClaw — autonomous coding and task-execution agents that use tool calling to interact with your system. Hermes works with any LLM provider (OpenRouter, Anthropic, OpenAI, Google, DeepSeek, xAI, local models, and 20+ others) and runs on Linux, macOS, Windows, and WSL.

What makes Hermes different:

- **Self-improving through skills** — Hermes learns from experience by saving reusable procedures as skills that load into future sessions.
- **Persistent memory across sessions** — remembers who you are, your preferences, environment details, and lessons learned. Pluggable memory backends.
- **Multi-platform gateway** — the same agent runs on Telegram, Discord, Slack, WhatsApp, iMessage, Signal, Matrix, Teams, Email, and a dozen more platforms with full tool access, not just chat.
- **Many surfaces** — the same agent core drives the CLI, the Ink TUI, a native Electron desktop app, a web dashboard, and an ACP server for IDEs (VS Code / Zed / JetBrains).
- **Provider-agnostic** — swap models and providers mid-workflow; credential pools rotate across multiple API keys automatically.
- **Profiles** — run multiple independent Hermes instances with isolated configs, sessions, skills, and memory.
- **Extensible & themeable** — plugins, MCP servers, custom tools, webhook triggers, cron scheduling, skins that theme every surface, desktop UI plugins, TUI widgets, and pet mascots.

**This skill is a hub.** The body covers identity, quick start, spawning/orchestration, and hard invariants. Everything else lives in reference files — **load the matching reference (below) before answering**; do not answer detail questions from the body alone.

## Quick Start

```bash
# Install (shell installer — bootstraps PM, Python, dependencies, and the launcher)
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash

# Interactive chat (default surface; set display.interface: tui to launch the Ink TUI instead)
hermes

# Single query
hermes chat -q "What is the capital of France?"

# Setup wizard  /  pick model+provider  /  health check
hermes setup
hermes model
hermes doctor

# Other surfaces
hermes desktop                 # launch the native desktop app (alias: hermes gui)
hermes dashboard               # web admin panel + embedded chat
hermes proxy                   # OpenAI-compatible local proxy backed by your OAuth provider
```

## Spawning Additional Hermes Instances

Run additional Hermes processes as fully independent subprocesses — separate sessions, tools, and environments.

### When to Use This vs delegate_task

| | `delegate_task` | Spawning `hermes` process |
|-|-----------------|--------------------------|
| Isolation | Separate conversation, shared process | Fully independent process |
| Duration | Minutes (bounded by parent loop) | Hours/days |
| Tool access | Subset of parent's tools | Full tool access |
| Interactive | No | Yes (PTY mode) |
| Use case | Quick parallel subtasks | Long autonomous missions |

### One-Shot Mode

```
terminal(command="hermes chat -q 'Research GRPO papers and write summary to ~/research/grpo.md'", timeout=300)

# Background for long tasks:
terminal(command="hermes chat -q 'Set up CI/CD for ~/myapp'", background=true)
```

### Interactive PTY Mode (via tmux)

Hermes uses prompt_toolkit, which requires a real terminal. Use tmux for interactive spawning. `tmux send-keys -t agent1 'text' Enter` in one call submits: Hermes treats a lone Enter that ends a fast burst of input as a submit once input has stayed quiet for a quarter second, while the Enters inside a multi-line paste stay newlines. The recipes below send `Enter` as its own call after a short pause, which submits at once and does not depend on that timing. Both recipes wait for the `❯` input prompt (the default skin's symbol; use your skin's prompt symbol if you changed it) instead of a fixed sleep: a first start can take far longer than a few seconds, and input sent before the prompt is lost.

```
# Start
terminal(command="tmux new-session -d -s agent1 -x 120 -y 40 'hermes'", timeout=10)

# Wait for the input prompt (❯), then send a message
terminal(command="for i in $(seq 90); do tmux capture-pane -t agent1 -p | grep -q '❯' && break; sleep 1; done; tmux capture-pane -t agent1 -p | grep -q '❯' && tmux send-keys -t agent1 'Build a FastAPI auth service' && sleep 0.5 && tmux send-keys -t agent1 Enter", timeout=100)

# Read output
terminal(command="sleep 20 && tmux capture-pane -t agent1 -p", timeout=5)

# Send follow-up
terminal(command="tmux send-keys -t agent1 'Add rate limiting middleware' && sleep 0.5 && tmux send-keys -t agent1 Enter", timeout=5)

# Exit
terminal(command="tmux send-keys -t agent1 '/exit' && sleep 0.5 && tmux send-keys -t agent1 Enter && sleep 2 && tmux kill-session -t agent1", timeout=10)
```

**No tmux** (`command -v tmux` prints nothing, e.g. an older Hermes Docker image): run Hermes as a PTY background process and drive it with `process_manage`. Stdin only exists with `pty=true`. `submit` sends the text plus the Enter key a keyboard sends, and Hermes submits it the same way as a one-call tmux `send-keys`. The recipe below instead `write`s the text, pauses, and `write`s the Enter (`"\r"`) on its own, which does not depend on burst timing. Wait for the input prompt before the first write: during startup Hermes queries the terminal's colours and then flushes its input, so text written before the prompt appears is silently dropped.

```
terminal(command="hermes", background=true, pty=true)   # returns session_id
process_manage(action="log", session_id="<id>", limit=20)   # repeat, with terminal(command="sleep 1") between, until the ❯ prompt line shows
process_manage(action="write", session_id="<id>", data="Build a FastAPI auth service")
terminal(command="sleep 0.5")
process_manage(action="write", session_id="<id>", data="\r")
process_manage(action="log", session_id="<id>", limit=40)   # read the screen
process_manage(action="write", session_id="<id>", data="/exit")
terminal(command="sleep 0.5")
process_manage(action="write", session_id="<id>", data="\r")
```

## Surfaces (quick orientation)
