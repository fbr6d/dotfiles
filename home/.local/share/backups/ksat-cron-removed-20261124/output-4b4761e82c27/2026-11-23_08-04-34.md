6. 작업 승인과 실제 도구의 1회 보호 승인을 구분한다. 모든 작업자 카드 본문에 **“즉석 명령(-c, -e, heredoc으로 python·node 실행) 금지. 스크립트는 작업 폴더에 파일로 쓴 뒤 python3 파일.py로 실행”**을 그대로 넣는다. `create` 전에 완성된 본문의 문자열 포함 여부를 검사하고, 생성 뒤 `show --json`의 실제 본문과 대사한다. 준비용 조회도 보호 대상이므로 실행 ID 확인·JSON 해석 같은 첫 준비 행위까지 허용 도구와 명령 형식을 명시한다. 메타데이터용 코드라는 이유로 해당 실행 문맥의 즉석 실행 보호를 예외 취급하지 않는다. 필요하면 실행 프로필의 `hermes approvals test --json -- '<정확한 명령>'`으로 실행 없는 판정만 확인한다. `allow`는 실행 성공이 아니며, `ask-approval`·`deny`는 실행 전에 인계한다. 실행 전에 차단돼 파일이 바뀌지 않았더라도 실제 도구 응답의 `status`·`exit_code`·오류와 요청을 보존하고, 사용자가 정한 첫 보호 차단 중단 조건을 선택적인 문법 점검에도 먼저 적용한다. 스크립트 로그의 종료값 0·빈 stderr·자체 검사 통과로 도구 단계의 차단을 지우지 않는다. 승인창 연결이 검증되지 않은 비대화형 쓰기를 반복하거나 보호 설정을 완화하지 않는다. 필수 선행과 선택 검사의 구분은 총괄이 인계받은 뒤 허용 후속을 정할 때 사용하며, 작업자가 중단 조건을 스스로 면제하는 근거로 쓰지 않는다. 총괄은 확인한 제출물·입력과 미확인 범위를 나눠, 차단된 검사에 의존하지 않고 현재 승인이 허용하는 독립 작업만 잇는다. 미확인을 성공으로 메우거나 다른 도구·경로·담당에게 같은 차단 동작을 넘기지 않는다.
7. 다른 작성자에게 직접 반영을 요청하기로 사용자와 정했으면 기존 실행 배정을 정리한다. 총괄은 실제 백업 경로·반영 위치·파일 diff·필요한 확인값을 읽기 전용으로 검증한다. 카드의 예정 백업 경로를 실제 생성 경로로 보고하지 않는다.

## 3. 사용량·동시성·실제 착수를 확인한다

1. 최신 승인에서 공급자·계정·판단 창별 신규 착수 조건, 기존 실행 처리, 공급자별/전체 병렬 상한을 분리한다. 슬롯 여유나 한도 초기화를 공급자 상한 초과·옛 병렬도 복원 허가로 보지 않는다. 활성화마다 승인 근거·provider/fallback·실제 실행 수·입력·쓰기 충돌·자원을 확인한다. 판단 제외 창은 적용 범위를 기록하고 결정용 출력에서 빼되, 다른 창과 실제 공급자 오류는 계속 적용한다. 계측 불일치의 실제 호출 예외는 명시 승인된 범위에서 첫 카드의 지정 모델 응답·도구 활동으로 확인하고, 같은 의심 수치만으로 다시 보류하지 않는다. 실제 한도 오류에는 저장분·오류·미완료를 보고하며 계정·결제·모델·보호 변경으로 우회하지 않는다. 숫자·예외·과거 관측을 영구 기준으로 저장하지 말고, 속도 협의선·금지선의 구체 비교와 계측 절차는 `hermes-agent`의 provider 참고 문서를 따른다.
2. 사용량·실행 형식·실패 분류의 운영 기준 변경을 과목·목표·품질 기준의 계획 변경과 구분한다. 운영 기준만 바뀌었으면 계획서를 고치거나 같은 계획의 재승인을 요구하지 않는다. 적용 공급자·계정 창·모델/작업 종류·새 비교 조건·폐지할 옛 조건·승인 근거를 먼저 실행 원장에 기록하고, `list --json`으로 영향받는 카드를 추린다. 폐지된 일일 배분이나 임시 대기선을 더 보수적인 추가 조건이라는 이유로 계속 적용하지 않는다. 즉시 모델 교체 보류, 초기화 후 재개, 공급자별 병렬도, 검증분을 보존한 이어가기 같은 예외를 구분하고, 실행 유지 지시는 진행 중 카드를 끊지 않은 채 적용한다. 영향받는 현재 카드의 `edit --body`에 최신 조건이 과거 명세보다 우선함을 명시하고 각 `show --json`에서 정확히 반영됐는지 확인한다. 회수 사건이나 지연 알림이 옛 자동 전환 지시를 다시 실행하지 않도록 중지 결정을 제어 명령보다 먼저 기록한다. 대상 수와 반영 수를 대사하고 미반영 항목을 남긴다. 완료·취소 카드와 과거 댓글은 당시 이력으로 보존한다. 이후 새 카드에도 최신 조건을 잇되, 읽기 전용 계획서를 고치지 않으며, 사용률 중단선만 바뀐 것을 동시성 확대·모델/보호 설정 변경·작업자 재시작 허가로 해석하지 않는다. 동시성이나 모델 배정을 명시적으로 바꾼 최신 승인은 해당 범위에 적용하되 다른 범위까지 확대하지 않는다. 신규 착수 기준과 기술적인 계정 하드캡 구현은 구분하고, 사용자에게는 새 시작/중지 기준·반영 범위·유지한 조건을 짧게 보고한다.
3. 새 사용량·권한 심사가 필요한 후속 카드는 명시적인 운영 대기로 둔다. 부모가 끝나면 자동 실행될 `todo`를 새 심사 대기의 대체물로 쓰지 않는다. 준비·예산 대기를 품질 실패나 사용자 승인 거부로 표현하지 않는다.
4. 재개 후보는 개별 실패 근거로 기술 차단·권리 제한·본문 미보유·선행 대기를 나눠 실제 복구 의존 집합만 추린다. 요청 요약과 개별 기록이 다르면 차이를 보고한다. 병렬 상한보다 적격 카드가 적으면 가능한 수와 제외 사유를 밝히고 제한 항목이나 새 분할로 슬롯을 채우지 않는다. 독립 입력·쓰기 구역만 병렬화하며 프로필 수·예약 포함 점유·실제 작업자 수를 구분한다. 현재 run의 연결 작업자·PID/시작 식별·실행 임대·새 활동을 대조하고, 완료 카드의 종료 정리나 미종료 저장 세션을 실제 추론과 혼동하지 않는다. 활성화 직전에 승인 대상 전체의 최신 상태와 점유를 한 번 확인해 불명확하면 해당 신규만 대기한다. 사용량의 공급자·창·조회 시각·원값과 점유 스냅샷을 보관하고 게이트·변경 사유·인계문을 같은 값에서 만든다. 옛 숫자를 복사하거나 실제 실행과 예약을 같은 수치로 보고하지 않는다. 중복 담당·자기 완료 대기·불필요한 대기 작업자를 만들지 않고 변환 프로그램의 임시 프로필도 작업별로 분리한다. 세션·PID·계측의 구체 대조는 `hermes-agent` 참고 문서를 따른다.
5. 종료가 산출물 선행인지 공유 슬롯 대기 해제인지 구분한다. 자기 입력을 이미 인수한 독립 대기 작업은 정상 종료로 슬롯이 비면 새 착수 조건을 확인해 긴 종료 산출물 인수보다 먼저 활성화·감시를 연결한다. 종료 산출물을 소비하는 후속의 인수는 생략하지 않는다. 담당·본문·선행·단일 알림·배정 표시를 확인해 `unblock`한 뒤 `show --json`을 읽고, 이미 claim·spawn됐으면 중복 실행하지 않는다. 아직 `ready`인 대상만 빈 슬롯 수 이내에서 제한된 `dispatch`로 입장시킨다. 구체 순서는 `hermes-agent`의 background 참고 문서를 따른다.
6. 차단 해제, 실제 작업자 연결, 지정 모델의 응답·도구 활동을 별도로 확인한다. 카드 설정이나 PID 생존만으로 진행을 주장하지 않는다. 빈 `spawned` 목록과 잠깐의 `ready` 관측만으로 실패를 단정하거나 소스·설정 전면 조사로 넓히지 않는다. 네이티브 디스패처의 입장을 위한 제한된 대기 후 정확한 카드의 현재 run을 한 번 대조하고, 미입장이 지속되거나 명시적 오류가 있을 때만 한정 진단한다. 실제 시작이 확인되면 완료 대기용 반복 폴링을 하지 않는다.
7. 사건 발생·알림 게시·wake·실제 총괄 재진입·후속 활성화는 각각 확인하고 구독/코드만으로 자동 재개를 보장하지 않는다. 지연 알림은 최신 승인·원장·현재 run·사건 식별자로 대사해 과거 실패를 새 실패로 세거나 정상 실행을 바꾸지 않는다. 먼저 현재 알림의 카드·run·사건 종류·기존 처리 식별자·남은 인수 범위를 좁혀 대사한다. 앞서 제출 사실만 보고한 사건과 실제 인수·후속 조치까지 끝낸 사건을 구분한다. 기처리 범위가 완결됐으면 그 지점에서 종료하고 보고·첨부·인수·활성화를 반복하지 않는다. 미처리 범위가 남았으면 그 범위와 실제로 연결된 승인 후속만 처리해, 제출 접수를 인수 완료로 오인하거나 압축 요약의 다른 미완료 작업으로 옮겨 가지 않는다. 기처리 알림만 남았으면 전역 운영 위임·빈 실행 슬롯·압축 요약의 미완료를 근거로 다른 산출물을 인수하거나 새 카드를 등록하지 않는다. 지연 알림 확인과 실제 미처리 종료에 연결된 승인 후속을 구분해야 불필요한 범위 확대를 막을 수 있다. 미처리 여러 건은 통합 보고한다. 이미 처리한 게이트웨이 내부 알림만 남았으면 지원이 확인된 `NO_REPLY`를 번역·설명·머리말 없이 단독 최종 응답으로 사용한다. 빈 본문은 의도적 무응답이 아니라 오류·재진입으로 처리될 수 있으므로 반환하지 않는다. 이 제어 토큰을 새 사용자 질문이나 아직 보고하지 않은 결과를 숨기는 데 쓰지 않는다. 감시 exit0는 관측 종료이지 작업 성공이 아니다. 실제 사건 종류를 구독한 유한 단발 감시의 소유 핸들·시작 로그·초기 상태·running을 한 번 검증하고, 등록 중 종료된 카드 때문에 기다리는 루프를 만들지 않는다. 남은 승인 작업의 감시는 긴 인수보다 먼저 연결한다. 종료된 감시의 교체를 기본으로 하되 대상 변경·확인된 사건 누락일 때만 자기 관측을 종료하며 실제 작업자·게이트웨이는 중지하지 않는다. 명령·등록 경쟁·지연 사건의 구현은 `hermes-agent`의 background 참고 문서를 따른다.

8. 대형 원문 검수에서 입력이 비대해지면 현재 문항 ID·쪽·필드·그림 영역만 선별하고 완료한 원문을 다시 출력하지 않는 안을 우선 검토한다. 사용자에게는 승인된 범위 안의 읽기 배치 축소와 카드·세션·최초 봉인 단위의 추가 분할을 구분해 제안하며, 후자는 승인 전에 실행하지 않는다. 재개 인계는 검증 상태·근거 경로·입력 확인값·남은 ID 중심으로 구성하고, 이전 전체 대화나 원장을 다시 주입해 긴 문맥을 재현하지 않는다. 토큰 계측과 새 세션의 입력 설계는 `hermes-agent`의 provider 참고 절차를 따른다.

## 4. 검수·수정·인수·취소를 처리한다

1. 제작자의 자체 점검과 제작에 참여하지 않은 담당의 독립 검수를 분리한다. 정답 유일성·공식 범위·해설·개념 연결·문학 출처·PDF 전 쪽 가독성 등 승인된 항목을 실제 확인한다. 구조 전수·의미 표본·의미 전수와 미검증을 혼동하지 않는다. 블라인드 검수 활성화 전에는 총괄이 `hermes kanban --board ksat-10000 context <카드>` 등 현재 지원되는 조회로 실제 조립 맥락까지 검사한다. 자동 주입되는 댓글·이전 시도·부모 결과·최근 역할 이력에 풀이·연결 판단이 들어갈 수 있으므로 새 모델·세션·run·카드만으로 깨끗한 시작을 보장하지 않는다. 이미 노출된 판단을 무시하라는 지시나 이력 삭제·댓글 밀어내기로 무노출을 주장하지 말고, 조건을 확인할 수 없으면 실행하지 않은 채 원인·대안을 사용자에게 먼저 보고한다. 조건을 충족한 검수자에게 해당 분할의 원문 문제만 먼저 제공하고, 분할 전체의 첫 판단·근거를 저장해 해시·시각으로 봉인한 뒤 정답·해설·연결 원장·기존 검수·정답 노출 가능 Wiki를 열게 한다. 전체 재시작이 승인된 경우에는 이전 부분 판정·봉인을 보존만 하고 새 결과에 승계하지 않는다. 기존 이력은 도구에 출력하기 전에 현재 분할 ID로 필터한다. 과거 또는 부수적 정답 노출은 후속 카드에 정답 없는 ID만 인계하고 새 독립 첫 일치에서 제외한다. 봉인·노출·중단 보존의 세부 절차는 자료 기반 Wiki 참고 문서를 따른다.
2. `done`이 아니라 실제 판정과 수행 범위를 읽는다. 수정필요 판정도 계약에 따라 정상 인계할 수 있지만 도구/권한 때문에 판정 자체가 미완료이면 차단이다. 항목별 기록·구조 전수·연결 이유 검토를 의미 전수·완성 해설·권리 확인으로 승격하지 않는다. 집계 상태와 실제 확인 방식을 교차 대사해, ‘전체’ 안의 키워드 검출 전용·텍스트층 전용 항목은 해당 의미·기호 미확인으로 별도 인계한다. ‘미확인 0’ 같은 분류값을 실제 미검증이 없다는 뜻으로 쓰지 말고, A/B/B1 같은 근거 코드도 해당 자료의 정의를 확인해 다른 등급 체계로 옮기지 않는다. 지정 필드 통과와 같은 ID의 다른 미검증/보류 축, 대표 상태와 중첩된 잔여 집계를 분리한다. 안전 표지 누락이 결함이면 표지 필터만 믿지 말고 정확 ID·금지 행위를 후속 선정에 별도 적용한다. 문학의 시험 발췌/출전과 작품 전문/최종 저본/이용 권리도 구분한다. 승인 필드 밖 관찰은 원판정·확인된 잔여 불일치·미검증 단서로 나눠 총괄의 사용 제한·해제 조건과 함께 인계한다. 다른 회차의 같은 번호를 동일 문항으로 취급하거나 단서를 확정 오류로 만들지 않는다. 수정 한도가 끝났으면 관찰을 새 집필·전면 검수로 확대하지 않고 자동 후속에도 같은 한계를 전한다. 판정층·해설 작성 상태·필드별 인수 대사는 `references/source-grounded-wiki.md`를 따른다.
3. 최신 수정 승인이 유효하고 한도가 남았을 때만 같은 제작자의 수정 전용 카드와 같은 검수자의 재확인을 배정한다. 먼저 한도의 적용 단위가 전체 산출물인지 개별 문항인지 확인하고, 검수 카드 분할 수만큼 수정 회차를 늘리지 않는다. 같은 고정 판본을 읽는 최초 분할이 남았으면 수정 카드를 먼저 등록하되, 공유 입력을 바꾸는 실행은 관련 최초 분할 뒤에 연결한다. 그동안 확정된 필수 결함·정확한 쓰기 파일만 같은 승인 회차에 누적 인계한다. 마지막 선행이 종료되면 부모 목록의 완료 상태와 제출물의 총괄 인수 기록을 따로 대사하고, 미인수 자료를 확인한 뒤 기존 수정 카드의 입력·필드별 쓰기 경계를 확정한다. 그다음 최신 사용량·슬롯을 점검해 같은 카드를 활성화하며, 선행 `done`만으로 시작하거나 인수만 반복하고 적격 수정 배정을 남겨 두지 않는다. 최초 제출·판정·답 봉인·확인값을 보존하고, 승인된 마지막 재확인도 불통과면 추가 회차·검수자를 늘리지 않는다.
4. 기존 수정필요 카드에 댓글만 남기고 실행 배정을 대신하지 않는다. 같은 차단이 반복되면 실제 소유자·미충족 입력·새 run·의존성을 확인해 재실행 루프를 멈춘다. 자발적인 수행 한계 보고, 도구 반복 보호, 공급자 한도, 종료 프로토콜 위반을 구분하고 각각의 실제 근거로 조치한다. 사용자가 재실행을 금지하면 예산이 남아도 새 run을 시작하지 않는다. 대기 전환 뒤에는 카드 상태를 읽어 `blocked`·`triage` 등을 실제 값 그대로 보고한다. 반복 차단된 `triage`를 `needs_input`으로 재분류하려면 설치된 버전의 `block` 허용 상태를 먼저 확인한다. 해당 전환이 지원되지 않으면 실제 `triage`를 보존하고, 사용자 결정 필요 사유와 선택지는 9절의 카드 댓글로 기록하되 기술적인 상태·차단 종류가 변경됐다고 보고하지 않는다. 보호 판정 `allow`나 `BLOCKED` 댓글은 상태 전환의 성공 증거가 아니므로, 지원되지 않는 전환을 통과시키려고 먼저 `ready`로 올리거나 DB·보호 설정을 고치지 않는다. 수정본 없는 재검수나 강제 잠금 해제를 하지 않는다.
5. 미수정 보존·비교 보고만을 지시받으면 남은 수정 회차가 있어도 사용하지 않는다. 원고·PDF·검수 파일을 보존하고 결함 미해소·미인수·수정 횟수·재확인 상태를 그대로 보고한다.
6. 업로드 취소는 부모 보고 카드를 닫기 전에 처리한다. 미실행 카드는 사유와 이력을 남긴 취소 보관을 사용하고, 완료된 업로드로 닫거나 기록을 삭제하지 않는다. 이미 발생한 외부 효과는 정확히 확인하며 원격 파일을 임의 삭제하지 않는다.
7. 사용자가 작업자 재실행 없이 직접 마무리를 요청하면 기존 근거로 현재 대화에 실제 본문을 전달한 뒤 필요한 카드 전환만 한다. 생략하라고 한 사전 확인을 같은 목적의 다른 명령으로 되살리지 않는다. 종료를 위한 `unblock`의 재실행 경쟁과 수동 완료 run은 참고 문서 절차로 검증한다.
8. 카드·문안·제출 정합성 인수·독립 검수·총괄 인수·개인 보관·실제 보고·사용자 품질 승인·실제 학습은 별도 상태다. 제출 정합성 인수는 독립 검수에 넘길 판본·실파일·입력 보존·누락 여부를 확인하는 단계로 한정한다. 계약에 총괄의 추가 전수 검수가 없으면 검수자가 맡을 전 쪽·내용 검사를 먼저 복제해 착수를 지연하지 말고, 확인한 고정 입력과 예비 확인의 한계를 기존 검수 카드에 인계해 승인된 후속을 잇는다. 제한부 인수는 현행 승인에서 허용한 경우에만 대상 판본·인수 범위·허용 후속·잔여 미확인·사용 제한을 구분해 기록한다. 절차 보류 판본의 관리 목록 사용을 별도 승인받으면 실행 종료·절차 인수·관리 목록 사용·권리·품질을 각각 기록하고 원래 차단과 보류는 보존한다. 이 예외를 새 실행·원본 열람이나 향후 보호 차단 뒤 계속할 상시 허가로 확대하지 않는다. 누락 검증의 새 시점 보완 인수와 원실행 당시 절차 인수도 분리해, 현재 일치만으로 과거 미확인을 소급 통과시키지 않는다. 사용자가 미확인을 남긴 채 다음 단계 진행을 명시했으면 그 승인과 고정 입력을 소비 카드에 전달해 실제로 착수시키고, 과거 전역 준비 플래그를 같은 후속의 중지 조건으로 되살리지 않는다. 이 단계 전환을 독립 검수·권리 해소·전체 완전성·시험 적격·출판 승인으로 확대하지 않는다. 인수 결정과 실제 판본 표기 반영을 따로 검증하고, 버전·README 변경만으로 내용이나 소비 경로의 품질을 승격하지 않는다. 봉인 당시 상태는 보존하고 이후의 제한부 인수는 원장·운영 메타데이터에 별도로 기록해 읽어 확인한다. 현재 상태를 맞추려고 이미 봉인한 보고서·목록을 고치고 다시 봉인하지 않는다. 위키 정식판·디자인 견본·학습용 PDF 점검본처럼 산출물별 완료 기준이 다르면 각각 기록한다.

9. **학습 PDF는 판본별 마스터 선확인 게이트로 운영한다.** 제작자 자체 점검이 끝나면 총괄은 파일·판본·일차·쪽수·크기·해시만 최소 대조해 다른 인수·정리보다 먼저 검수 전·마스터 컨펌 대기로 첨부한다. 정확한 그 판의 OK 전에는 AI 최종 오류 검사·총괄 품질 인수·개인 보관을 시작하지 않는다. 사용자가 미컨펌 참고판으로 보존하라고 정하면 그 판의 OK 요청과 AI 검사 대기를 종료하고, 파일·봉인은 그대로 둔 채 카드의 제목·현재 결과·요약·메타데이터·다음 책임자만 맞춘다. 참고용 표지를 최종 품질 승인이나 인쇄된 판본 번호 변경으로 해석하지 않는다. 마스터 피드백 재제작과 AI 오류 검사 후 한정 수정을 별도 회차로 관리하고, 새판도 먼저 첨부한 뒤 그 정확 판의 OK를 받는다. 사용자가 여러 과목·판본을 모은 뒤 일괄 판단하기로 정했으면 제작본을 즉시 전달하되 개별 OK를 재촉하지 않고, 정확한 판본·경로·쪽수·변경점을 누적해 지정한 묶음이 갖춰졌을 때 한 번에 보고한다. 판단 보류 중인 판은 수정·재제작하지 않고 최종 검사·품질 인수·보관도 시작하지 않는다. 확인 대기를 다른 과목 전체의 선행으로 만들지 않되, 사용자가 모든 과목에 새 공통 양식을 지정했다면 그 양식의 선택·반영은 각 제작의 필수 선행으로 둔다. 구체적인 전환·전달 순서는 `references/learning-material-feedback.md`를 따른다.

## 5. 학습자료와 피드백의 상시 기준

- 친구가 옆에서 설명하듯 친근한 **해요체**, **쉬운 말 → 정식 용어**, 짧은 문단을 사용한다. 개념별 쉬운 설명용 예시나 비유, 중요성·출제 방식·실수 안내를 넣되 정의·조건·예외가 우선이다. 중요성·출제 방식·실수를 하나의 축약 항목으로 뭉치지 말고, 승인 원문의 각 요구를 체크표의 별도 항목과 실제 문장 위치에 대응시킨다. 제작자 체크표 자체가 요구를 빠뜨릴 수 있으므로 재확인도 승인 원문에서 출발한다. 출제 방식은 확인된 자료 안의 관측 형태와 학습 역할로 설명하고 새 출제 예측으로 메우지 않는다. 원문 문항·선지·정답은 말투 변경 대상이 아니다. 인쇄용 이모지는 쓰지 않는다.
- **설명 → 복기 질문 → 해설의 필수 대조표 → 누락 보고란**을 같은 세부 번호로 연결한다. 번호 존재뿐 아니라 필수 내용·조건의 완전성과 누락 판정 가능성을 검증한다. 자기 표현을 인정하고 통암기를 요구하지 않는다. 학습 내용이 아닌 운영·설계 메모는 암기·필수 복기·누락 채점에서 분리한다. 원값·원번호를 보존해야 하면 승인된 비대상 표지나 별도 분류로 보관하고, 등록 총수와 학습 필수 수를 따로 보고한다. 실제 학습 조건·예외까지 메모로 제외하지 않도록 의미와 승인 범위를 확인한다.
- 기호의 뜻·세는 대상과 단위·중복/제외·성립 조건을 드러내고 읽은 조건과 계산·변환을 구분한다. 사용자 관찰이나 오독을 공식 규칙·교재 오류로 검증 없이 채택하지 않는다.
- 단계 순서·시간표·암기법·다음 날 복습은 최신 승인 설계를 따른다. 과목별 근거 조사로 정하는 작업에서는 기존 인출·대조·보완 순서도 비교용 출발점이지 모든 과목의 고정 양식이 아니다. 학술 근거·실전 경험담·사용자 개인 효과를 구분한다.
- 개념 ID는 최신 승인 규약을 따른다. 형식 승인·영역/번호 승인·실제 파일 적용을 각각 확인하고, 형식이 승인됐으면 영역/번호가 미승인이라는 이유로 형식 전체를 다시 미정으로 돌리거나 재승인받지 않는다. 확인이 필요한 영역/번호만 기존 제안의 고유 개수·번호 범위·연속성·구 ID 대응 근거와 함께 제시한다. 임시→최종 전환을 승인받았으면 원판 보관·구 ID 대응표·참조 검사를 거쳐 적용하며, ID 선택 승인을 위키·PDF 품질 승인이나 보류 해제로 확대하지 않는다.
- 사진·시간·답 일치 수보다 사용자가 지정한 **기록 용도**를 먼저 확인한다. 품질 점검을 실제 학습·성취·진도 근거로 쓰지 않는다. 빈칸·미선택을 임의 판정하지 않고 실제 학습용 기록란이 있다는 이유로 수행을 인정하지 않는다.
- 단계 정정은 현재 제목·본문·요약·결과·메타데이터와 승인된 후속 지시에 일치시킨다. 과거 원문·검사 이력은 보존하고 피드백은 과목·판본·쪽·원문 근거·담당과 연결한다. 미접수 피드백을 완료로 채우지 않는다.
- 사용자 품질 승인 전 PDF는 **품질 점검본·검토용 제출·내부 회차 결과**로 표현한다. 예정 승인 시점이나 사이클 전환을 자동 승인으로 보지 않는다. 전 과목 재검토 방향이 무제한 수정 허가는 아니며 기간·마감·실제 학습 성과를 임의 확정하지 않는다.

## 6. 사이클·출처·개인 보관

- 사이클은 일차·판본·run과 다르다. 같은 사이클의 승인된 비교 판본은 기존 문항 원장의 참조로 연결하고 새 고유 문항으로 중복 집계하지 않는다.
- 새 사이클은 과거 **모든 사이클**의 사용 문항과 대조해 다른 원문을 쓴다. 파일명·미러·책형·문항코드만 달라도 같은 원문일 수 있다. 원문 부족·식별 불명은 재사용·AI 대체·분량 축소로 메우지 말고 해당 범위만 보류한다.
- 과목별 manifest의 식별자·원본·쪽/좌표·개념 연결·공식 정답 근거 위치를 원장에 남긴다. 정답값의 불필요한 복제로 후속 독립 풀이에 답을 노출하지 않는다. 미등록 과목을 문항 0개로 채우지 않는다.
- 문항 출처·AI 사용 예외·검증 조건은 최신 승인과 현재 `AGENTS.md`를 함께 읽어 적용한다. 제한된 과목·지문 예외를 다른 과목이나 심화 단계 전체의 허가로 확대하지 않는다. 국어 문학은 기존 원문·출처·이용 조건을 확인하고 창작·개작·가상 출전으로 메우지 않는다.
- 학습법 근거는 자료의 연구 설계·확인된 전문 역할, 해당 주장, 조사자가 조합한 실행안, 사용자 개인 효과를 나누어 판정한다. 합의된 A/B/C/D 체계에서 C는 확인된 전문가·기관의 권고이지 대조실험 효과의 보증이 아니다. 자기표명만 확인한 조언은 D 또는 전문성 미확인으로 한정하고, 같은 자료 안에서도 방법 권고와 효능·홍보를 구별한다. 조사자가 절차를 조합했다는 이유만으로 새 실행안에 C를 붙이지 않는다.
- 자료 보유와 복제·변형·모델 전송·공개 권한을 구분한다. 개인 iCloud 예외는 검수·인수된 대상 PDF의 지정 경로 보관에만 적용한다. 공개·공유 링크·다른 업로드로 확대하지 않는다. 단, 학습지·해설 PDF는 생성이 끝나면 `#통합-프론트엔드` 보고에 파일을 첨부한다(2026-11-20 사용자 결정, AGENTS.md 10절; 검수 전 판은 '검수 전' 표시, 원본 시험지 PDF·원문 이미지는 첨부 안 함).
- 보관은 기존 경로 충돌을 먼저 확인해 새 판본 폴더를 사용하고 기존 파일을 덮어쓰거나 삭제·이동하지 않는다. 업로드 뒤 정확한 원격 파일명·`rclone lsl` 크기를 로컬과 대조한다. 보호에 막히면 **iCloud 업로드 대기**로 반환하며 미실행·부분 전송·검증 실패를 구별한다.

## 7. 모델·판본 비교

- 디자인 참고는 정상 공개 정보로 선정한 인강 대표 강사의 개념 교재를 우선하고 일반 개념서는 보조 비교로 구분한다. 선정 인원·교재 수·조사 순서는 현행 승인에서 읽으며 예시 이름을 확정 명단으로 쓰지 않는다. 사이트의 대표 표시·수강생 수·판매 순위는 원래 기간·범주·URL과 함께 기록하고 전국 절대 순위나 학습 효과로 확대하지 않는다. 세부 과목의 지표를 통합 과목의 순위로 승격하지 말고 조건부 근거와 한계를 표시한다. 로그인·결제·수강생 전용은 건너뛰고, 쪽 단위 본문 표본과 부분 이미지만 확인한 교재를 별도 집계한다. 개념 교재라는 서지와 실제 표본이 개념 설명 쪽이라는 판독을 구분한다. 문제·해설 배치만 본 경우 개념 정리표·암기·빈 복기 장치를 관찰했다고 하지 말고, 미관측 요소의 제안은 우리 자료의 독자 설계로 표시한다. 비공개·미발견·접근 오류·표지/목차만 공개를 구분하고 미조사 수량을 0으로 채우지 않는다. 부족분 보완은 확인된 교재·쪽을 불변 승계하고 미충족 ID·필드만 새 카드에 배정하며, 부분 조사 제출의 인수를 전체 기준 충족으로 표현하지 않는다. 외부 캡처는 로컬 조사 근거로만 두며 본문·문항·도식·캐릭터·로고·브랜드 표현을 산출물에 옮기지 않는다.
- 디자인 변경 전 **기존 양식 개선인지, 조사 근거 전용 재설계인지** 현행 승인에서 먼저 구분한다. 조사 근거 전용이면 허용된 리서치의 관찰 사실·적용 제안만 시각 설계 근거로 쓰고, 이전 색 역할·스타일 값·후보·최근 역할 이력을 기본값이나 새 디자인의 출발점으로 되살리지 않는다. 기존 학습판은 내용·원문 보존 입력과 시각 설계 입력을 분리한다. 사용자가 과거 팔레트나 색 역할의 재사용을 명시 승인하면 그 항목만 시각 입력에 복원하고, 과거 배치·강조 상한·후보 선택 절차까지 함께 되살리지 않는다. 조사 제안 안에 남은 옛 색 의미·선택 절차도 현행 승인과 대조해 효력이 없는 부분을 제외한다. 각 디자인 결정에 교재·쪽·관찰/제안 ID를 연결한다. 사용자가 컬러를 명시하면 정확한 팔레트의 외부 실측값이 없다는 이유로 흑백 기본값으로 되돌리지 않는다. 컬러 피드백에서는 지정된 강조색 수(3~4색), 진한 본문, 원문 문항 이미지 무색칠 조건을 먼저 잠근다. 소주제 색 띠·옅은 소제목·자체 도식 밑 연한 면·원문 밖 번호 강조의 관찰 근거와, 우리가 새로 고른 색값·틴트·적용 위치를 색 결정표에 나누어 기록한다. 교재 브랜드색을 복제하거나 독자 색값을 외부에서 측정한 값으로 표현하지 않는다. 화면 대비·흑백 시뮬레이션과 실물 인쇄 검증도 구별한다. 명시적 컬러 요구와 근거가 모두 없는 항목에만 흑백 본문·얇은 회색 선 같은 중립 기본값과 ‘조사 근거 없음’을 적용한다. 기존 후보 선택이 새 설계 방식으로 대체되면 현재 선택 요청을 종료하되 과거 파일·추천·보고는 보존하고 어떤 후보도 선택됐다고 기록하지 않는다.
- 디자인 전달은 **조사 인수 → 실제 학습 내용의 견본·필요한 결정표 → 현행 계약에 따른 후보 선택 또는 새 양식 컨펌 → 승인된 범위만 실제 반영**으로 진행한다. 번호 후보 계약에서는 완성형 한 번호 선택인지 요소 조합인지 밝히고, 제작자 추천과 실제 견본을 읽은 총괄의 추천을 분리해 후보별 추천 여부·추천 집합을 고정한다. ‘총괄 추천대로’는 그 보고의 집합에만 연결하며 미선택 후보나 미승인 조합을 함께 반영하지 않는다. 하나의 새 양식 컨펌 계약에 옛 후보 번호 선택을 다시 요구하지 않는다. 총괄 비교는 전달 빌드 식별 → 전체 쪽 개요 → 필요한 역할별 확대 표본 순서로 수행하고, 활자·여백·필기 공간의 절충과 확대·인쇄 조건을 보고한다. 조사 기록 인수·확보 목표 충족·확인 표본에 한정한 견본 제작 허용은 따로 판정한다. 근거 미달 상태의 후속 제작 허용이 불명확하면 해당 착수를 보류하고, 허용되면 소비할 교재·쪽·관찰 요소를 고정한다. 시안 제작 허가를 현행 양식 채택으로 확대하지 않는다. 양식 컨펌과 그 양식으로 재제작한 정확한 학습 PDF의 OK도 별도 게이트로 두며, 디자인 전용 이관의 내용·원문·시간·번호 연결을 보존한다. 독립 위키 작업에 디자인 대기를 불필요한 선행으로 추가하지 않는다. 상세 절차는 `references/material-model-comparison.md`를 따른다.
- **같은 내용의 다안 디자인 비교는 내용 잠금 → 축 조합표 → 실제 쪽 구조 대조 → 사용자 선택 순서로 진행한다.** 모든 안에 같은 개념·복기·표/도식·원문 문항과 필요한 공동 지문을 고정하고 기준안과 변경안을 구분한다. 승인된 구성·정보 계층·강조·색 양·밀도·표/그림 배치의 조합은 도구로 중복을 확인하고, 실제 쪽 개요에서도 구조 차이를 확인한다. 색조만 다르거나 조합표만 고유한 안을 서로 다른 디자인으로 세지 않는다. 각 안의 큰 번호·특징 한 줄·축 비교표·번호별 쪽 대응을 일치시키고, 원문 이미지와 진한 본문의 보존을 따로 점검한다. 한 번호 또는 허용된 요소 조합을 사용자가 고르기 전에는 공통 양식을 확정하지 않는다. 구체적인 비교팩 잠금·대사는 `references/material-model-comparison.md`를 따른다.
- **선택한 양식의 최소 수정은 선택 확정 → 변경·불변 목록 잠금 → 수정 견본 → 정확판 선첨부·OK → 승인된 전체판 반영 순서로 처리한다.** 이 사용자의 「자주 하는 실수」 안내는 제목과 본문이 있는 주의 역할색의 독립 칸으로 만들고, 다른 상자 안의 문장이나 소제목만으로 대신하지 않는다. 선택한 안의 글자 크기·행간·색·여백·표/도식·복기/공동지문/원문 배치를 잠그고, 요청한 수정에 필요한 국소 이동만 허용한다. 내용 생략·재서술·글자 축소·다른 후보 요소 혼합으로 쪽수를 맞추지 않는다. 번호 선택 완료와 수정 견본의 OK를 구분하고, 후속 제작이 이미 조건부 승인됐다면 정확한 견본 OK 뒤 같은 범위를 다시 승인받지 않는다. 선택안 재현·국소 변경 대사는 `references/material-model-comparison.md`를 따른다.
- 독립적인 동일 조건 제작과 기존 내용·검수·디자인을 참고하는 취합 개선을 먼저 구분한다. 승인된 입력 잠금과 새 쓰기 영역을 지키고, 개선 실험을 완전 독립 모델 시험으로 포장하지 않는다.
- 최신 승인에서 카드 종류별 모델·공급자 배정표를 확인하고 해당 카드에 고정한다. 프로필 기본 모델, 카드 override, 실제 run의 모델은 구별하며 기본값 변경을 진행 중·완료 카드의 교체나 재실행 허가로 해석하지 않는다. 수정 카드는 제작 모델을 잇고, 같은 판정을 이어가는 검수 재확인은 별도 변경 승인 없이 최초 판정의 실제 모델·공급자를 바꾸지 않는다. 상위 단계의 전체 최종 판정에 다른 모델이 승인됐으면 그 판정과 기존 판정의 변경·영향 재확인을 구분해 실제 diff에 필요한 최소 범위만 연결한다. 이를 추가 전면 감사나 수정 회차 확대에 이용하지 않는다. 프로필 기본값·fallback을 임의 변경하지 않으며 제작과 검수가 같은 모델이거나 동일 문항 검수 이력이 있으면 한계를 밝힌다.
- 요청된 **모든 판본**의 학습지·해설 절대경로·판본·실제 쪽수, 최초 지적 개수/내용·수정 횟수·재확인, 같은 개념의 실제 문단·쪽·대표 렌더 로컬 경로, 단계별 시간·사용량·총괄 의견을 대응시킨다. iCloud는 실제 확인·사용자 진술·예정·대기·취소를 구분한다.
- 내용 정확성·설명·복기 연결과 디자인·수식 가독성을 나눠 평가한다. 렌더 DPI·색 공간이 다르면 밝히고 픽셀 크기를 같은 조건의 측정으로 쓰지 않는다. 글자 크기·가로/세로 배율·줄 간격을 구분해 설명하고 가로 늘이기만으로 글꼴 pt가 커졌다고 단정하지 않는다. 기계 검사·대비·쪽수만으로 무오류나 학습 효과를 주장하지 않는다.
- 실제 run 시간과 종료 후 저장 세션의 입력/출력·캐시·추론·호출을 읽는다. 전후 사용량 비교 대상은 착수 전에 카드·run으로 특정하고, 실제 조회 시각과 run 종료 시각을 함께 기록한다. 먼저 끝난 다른 카드의 수치를 비교 대상의 종료값으로 대체하지 않으며, 관측을 놓쳤으면 최초 사후 조회와 지연을 명시하고 종료 직후 측정으로 표현하지 않는다. 중간값·계정 사용률·작업 사용량·추정 비용·실제 청구를 구분하고 정의가 다른 토큰을 임의 합산하지 않는다. 총괄 의견은 사용자 최종 승인이나 모델의 보편적 우열이 아니다.

## 8. 알림·사용자 보고·마무리

- 사용자 협의와 실제 보고는 총괄이 맡고 역할 봇은 카드 사건만 알린다. 승인된 `#통합-프론트엔드`의 현재 이름·ID·guild·접근·프로필을 확인한다. 사용자에게 숫자 ID 대신 실제 채널명을 표시하고 폐기·미확인 채널/스레드를 재생성하거나 대체하지 않는다.
- 일반 지시의 모든 단계는 **[일반]**, 계획 실행의 진행·차단·중간 산출물은 **[계획-진행]**, 그 계획 전체를 실제 검증한 최종 브리핑만 **[계획-최종]**이다. 한 보고에 머리말 하나만 쓰고 다른 머리말로 중복 게시하지 않는다.
- 새 카드마다 담당 봇의 Discord `notify` 구독 하나와 `배정: <카드 ID> <제목> → <담당>` 표시를 남긴다. 부모에서 상속된 알림 소유자도 재조회한다. 소유자 충돌이 있어도 현재 승인이 기존 구독 삭제를 금지하면 해제·재등록하지 않는다. 새 카드에서는 초기 `blocked` 상태로 담당 구독을 먼저 등록하고 부모를 나중에 연결하는 순서를 검토하며, 기존 카드의 의존성을 풀어 이 순서를 흉내 내지 않는다. 삭제·재등록이 허용된 경우에만 정확한 충돌 구독을 교체하고, 다른 Desktop/API wake와 origin의 실제 채널 유형·guild·thread를 보존한다. 구체적인 등록·읽기 검증은 `hermes-agent`의 background 참고 문서를 따른다.
- `notify`의 사건 게시, `wake` 요청, 실제 총괄 재진입·후속 배정은 별도다. 자연 발생 사건의 실제 메시지와 소비를 확인하기 전에는 구독·cursor만으로 자동화 성공을 주장하지 않는다. 가짜 완료·차단으로 알림 시험을 하지 않는다.
- **silent 전송은 금지한다.** API 전송은 `flags=0`과 의도한 멘션 동작을 명시하고 정확한 메시지를 읽어 대상·작성자·본문·첨부·flags를 검증한다. 알림 억제 해제와 휴대폰 실제 푸시 도착은 다르며 임의 멘션으로 설정을 우회하지 않는다.
- 보고문안과 실제 전달을 구분한다. 현재 대화에서 직접 보고하라는 지시는 이 대화에 본문을 싣고 별도 REST로 중복 전송하지 않는다. 사용자가 생략한 사전 확인을 재시도하지 않되, 실제 외부 API 게시 후 검증 의무와 혼동하지 않는다.
- 검토용 제출은 실제 존재 확인한 학습지·해설 각각의 **전체 절대경로·판본·쪽수·점검본 상태**를 쓴다. 폴더·카드 ID만으로 대신하지 않고 예정 파일은 예정으로 표시한다. 경로 안내는 첨부 허가가 아니다.
- 차단은 해결을 기다리지 말고 요청 유형에 맞는 머리말로 보고한다. 발생한 일·영향·확인된 원인/미확인·완료/미완료·해제 조건·다음 책임자를 구분한다. 전송 실패는 미전송으로 기록하고 중복 게시·임의 목적지 전환을 하지 않는다.
- 사용자 요청을 처리하는 동안에는 현재 작업 내용을 한 줄로 요약하되, 사용자가 다음 보고의 산출물·시점을 지정했다면 그 보고 게이트를 우선한다. 이미 처리한 내부 알림 때문에 정상 진행 보고를 반복하지 않는다. 필수 승인·한도·안전 차단은 정상 중간보고와 구분해 알린다. 진행 요약은 실제 도구 실행이나 검증 후 결과 보고를 대신하지 않는다.
- 진행 보고는 기준시각·현재 증거·완료 범위·대기/차단·조치·다음 담당 순으로 간결하게 쓴다. 상세 요청은 실제 결과를 빠짐없이 담되 프롬프트를 무조건 복제하지 않는다. ETA보다 수정 미배정·인계 공백을 먼저 확인한다. 예상 종료를 요구받으면 현재 남은 단계·최근 실측 또는 작업자 견적·관측 시각·산정 주체를 함께 밝히고 조건부 범위로 제시한다. 임의로 더한 시간이나 시각 계산의 성공을 처리 속도 근거로 삼지 말며, 근거가 부족하면 미정으로 남긴다. 전제가 깨지면 이전 예상을 정정하고 실행 상한을 ETA나 사용자 마감으로 바꾸지 않는다.
- 사람에게 보이는 티켓·댓글·오류·인계는 상세하고 띄어쓰기·문법이 정확한 한국어로 쓴다. 초보자에게 필요한 용어 설명을 붙이고 원본 식별자·명령·경로는 보존한다. 요약 첫 줄은 결과·남은 일·다음 담당을 담은 **180자 이내 한 문장**, 상세는 다음 줄이다. Discord에서는 표 대신 항목을 쓴다.
- Desktop 지시는 원문과 보고를 Desktop에도 같은 내용으로 유지한다. Discord 전송 사실 한 줄로 보고를 대체하거나 요약본과 상세본을 동일한 보고라고 하지 않는다. 실제 동기화 구현은 별도로 검증한다.
- 변경 전에 직접 작성한 본문·캡션·사유와 **완성된 전체 명령**의 정상/오류/재진입/종료 분기를 검토한다. 보고·사유·요약·분기별 안내를 처음부터 정확한 한국어 변수로 완성해 검사하고, `--reason`·`--summary`·댓글·`printf`에는 확인한 변수를 전달한다. 변수 일부만 검사한 뒤 다른 인자에 새 문구를 직접 쓰지 않는다. 검사 뒤 문구나 분기를 추가하면 완성된 명령을 다시 검토한다. 인라인 새 문구·불필요한 무동작 출력·외국어 자리표시자·나중에 덮어쓸 초기 대입도 남기지 않는다. 한자·일본어 혼입과 개행/탭 외 제어문자를 검사하고 문장도 직접 읽으며, 문자 검사 통과를 문법 검증으로 부르지 않는다. 원문 인용·식별자·명령·경로·도구 응답은 임의 번역/정규화하지 않는다. 조회 키와 경로는 실제 출력에서 그대로 가져오고, 뜻을 번역한 가상 키·장식용 투영 필드·무동작 루프를 넣지 않는다. 잘못 만든 키의 null은 원자료 누락처럼 보일 수 있으므로, 꼭 필요한 필드만 조회하고 필수 키의 실제 존재 여부를 확인한다. 확인한 공통 안내문은 재사용하고 대상과 실제값만 바꾼다. 변경 뒤 정확한 현재 상태·효과·잔여를 읽으며, 검증 필터 실패가 앞선 변경을 취소한 것으로 가정하지 않는다. 성공한 조치의 문구만 틀리면 원기록에 정정 댓글을 남기고 상태 전환·게시·실행·감시를 반복하지 않는다. 행정 종료 run과 실제 작업자 실행을 구분하고 잔여 차단은 실제 목록에서 집계한다.

## 9. 총괄 자율 판단·마스터 예외·미쿠 인계

### 상시 위임과 결정 경계를 먼저 확인한다

- 사용자가 지정한 실행 원장의 최신 마스터 결정에서 총괄 자율 위임의 유지·변경·회수를 확인한다. 압축·재진입 뒤에도 원장을 다시 읽고, 이 스킬이나 개인 기억을 승인 원본으로 삼지 않는다.
- 위임이 유효하면 승인된 계획서·기존 마스터 결정과 **품질 유지·보수적 선택·보존 우선**을 기준으로 일반 운영 결정을 직접 내린다. 애매하면 보류·한정 인수·제외·범위 축소를 고르고 가능한 독립 작업을 잇는다. 사용자 답을 기다리느라 적격 실행을 비워 두지 않되 슬롯을 채우려고 선행·권한·사용량 조건을 생략하지 않는다.
- 한정 인수·보류·제외, 같은 담당의 정정·보완·재확인 추가 1회와 한정 예외 수정, 승인 범위 안의 카드 분할·순서·모델 배정은 총괄이 판단한다. `raw/` 밖의 권리 미확인 자료는 빼고(`raw/` 전체는 2026-11-22 사용자 결정으로 개인 학습용 사용 승인) 채울 수 없는 칸은 빈자리로 남긴다. 기존 독립 검수·모델별 역할·사용량·동시성·명시된 중지와 보존 조건은 유지한다.
- 실패를 집계하기 전에 실제 요청·응답, 실패 코드 위치, 입력 상태와 위반한 계약을 대조해 내용 결함·검사 구현 오류·실행 형식 차단·권한 거부·공급자 오류를 구분한다. 오류 이름·종료값·카드 상태가 같다는 이유만으로 같은 원인으로 합치거나, 이름이 다르다는 이유만으로 다른 원인으로 나누지 않는다. 내용 수정 횟수·기술 원인별 반복 한도·재개 조건은 최신 승인이 정한 단위로 각각 적용하고 일반 반복 기준으로 명시된 예외를 덮지 않는다. 내용 판정에 영향을 줄 수 있는 오류를 기술 오류로 돌려 한도를 피하지 않는다. 새 카드·새 run이 승인됐으면 지정한 원인·잔여 범위만 이어가고 원차단·미완료·모든 실패 이력을 승계한다. 카드·모델·파일명 변경으로 한도를 초기화하거나 과거 절차를 소급 통과시키지 않는다.
- 작업자는 승인된 기대 음성 시험 밖의 첫 비0·필수 거짓·실행 전을 포함한 보호차단에서 실행과 코드 수정을 함께 멈춘다. 기대 음성은 사전에 범위와 예상 오류를 정한 저장 시험 안에서 관측하고 시험 프로세스는 0으로 마쳐 실제 명령 실패와 구별한다. 실패를 낸 코드·결과·로그는 그대로 두고 허용된 실패·인계 기록만 작성해 총괄에게 반환한다. 재실행하지 않았더라도 같은 run의 사후 패치·덮어쓰기는 보존 준수가 아니므로, 인수 때 재실행 유무와 코드 변경 유무를 각각 확인한다. 사후 처리의 자율 위임은 실제 도구 승인이나 보호 우회 허가가 아니다. 한정 인수·새 시점 보완으로 과거 절차를 소급 통과시키거나 차단 응답의 대체 방법 권고를 승인으로 다루지 않는다.
- 위임이 유효할 때 이 스킬의 일반적인 사용자 확인·승인 대기 문구는 아래 **여섯 예외**에만 적용한다. 상위 지침·실제 도구 보호·새로운 명시적 금지를 넘는 권한으로 해석하지 않는다.
  1. 학습 PDF·위키의 최종 품질 OK. 사용자가 정한 5과목 PDF 묶음이 준비되면 일괄 요청한다.

  4. 원본·결과·봉인 삭제나 덮어쓰기 등 되돌릴 수 없는 일.

### 사용자 결정 표식과 인계를 구분한다

- 위 여섯 예외 가운데 사용자 선택·승인 없이는 진행할 수 없는 안건만 카드 댓글 또는 실제 차단 사유의 **맨 앞**에 `[마스터 결정 필요]`를 붙인다. 그다음 한두 문장으로 사용자가 무엇을 골라야 하는지, 결정 전 무엇이 대기하는지 쓴다. 첫 줄은 기존 알림 규칙대로 180자 이내 한 문장으로 하고, 두 번째 문장이 필요하면 다음 줄에 쓴다.
- 총괄이 승인된 범위에서 스스로 해결할 수 있는 오류·자료 접근 실패·일반 진행 보고에는 이 표식을 붙이지 않는다. 단순히 `blocked`라는 이유만으로 사용자 결정을 요구하지 않으며, 이미 결정된 내용을 다시 묻지 않는다. 사용자가 한정 확인 후에도 미확인인 자료는 제외하고 진행하도록 정했으면 확인 범위·횟수·정확 제외 식별자·소비 제한을 카드에 명시하고, 결과를 보류·제외 목록으로 인계한다. 같은 안건을 재질문하거나 확인 회차를 늘리지 않으며, 해당 자료 없이 진행할 수 있는 적격 후속에는 그 확인 카드를 완료 부모로 걸지 않는다. 별개의 새 권한·보안 문제까지 이 제외 결정으로 해소됐다고 간주하지 않는다.
- 사용자의 결정이 **실제로 반영되고 확인된 뒤**, 같은 카드에 `[마스터 결정 반영]`으로 시작하는 댓글을 남긴다. 어떤 선택을 어떻게 반영했는지와 필요한 승인 근거를 짧게 적는다. 승인 접수·제안·반영·검증을 혼동하지 않고, 아직 구현·확인이 끝나지 않은 일을 반영 완료로 닫지 않는다.
- 한 카드에 여러 결정 안건이 있으면 짧은 안건명을 밝혀 필요·반영 댓글의 대상을 대응시킨다. 한 안건의 반영 댓글이 다른 미결 안건까지 해결한 것처럼 보이지 않게 한다. 공통 결정은 대표 원장 한 곳에 상세히 기록하고 관련 카드에는 그 카드에 필요한 입력·쓰기·선행·중지 조건의 차이와 참조 위치만 자립 명세로 전달한다. 긴 공통 결정·전체 보드 현황·모든 과거 본문을 카드마다 반복 복제하지 않는다. 현재 명세는 최신 조건으로 정리하고 이전 값은 변경 이력·댓글·보존 메타데이터로 추적해 시작 맥락과 명령 인자 크기가 불필요하게 커지는 것을 막는다.
- 작업자도 같은 표식을 사용하되 사용자에게 직접 질문·승인 요청·상담하거나 임의로 DM하지 않는다. 필요한 선택과 근거를 Kanban으로 총괄에게 전달하고, 총괄이 사용자 협의와 실제 반영을 책임진다.
- 사용자는 **미쿠의 5분 표식 확인·사용자 DM 알림이 이미 작동 중이며 총괄의 확인 사항이 아니라고 명시했다.** 별도의 명시적 요청 없이 총괄이나 KSAT 작업자가 미쿠 알림을 점검·재설정·재구현하거나 관련 예약·스크립트·설정·인증을 변경하지 않는다. 기존 알림을 재확인하느라 총괄의 표식 기록·작업자 전달을 지연하지 않는다.
- 총괄은 사용자 결정 필요성 판단, 카드 댓글·차단 사유의 맨 앞 표식, 한두 문장의 선택 요청, 같은 카드의 실제 결정 반영 기록, 작업자에게 규칙 전달을 책임진다. 일반 본문에서 규칙을 설명하며 인용한 표식을 새 결정 요청으로 쓰지 않으며, 스킬 저장·공지 전달·작업자 수신 확인은 서로 구분한다.
- 현재 작업에는 승인된 Kanban 댓글·본문 또는 검증된 통신 경로로 규칙을 전달하고, 이후 새 작업 배정에도 필요한 맥락과 함께 명시한다. 실행 중 카드의 본문·댓글 편집을 작업자의 실제 수신·적용으로 세지 말고 작업자의 확인이나 실제 결과의 새 기준 반영을 별도로 검증한다. 중단 금지인 실행을 변경 전달 목적으로 재시작하거나 확인되지 않은 세션 주입·인증 경로를 만들어 쓰지 않는다. 완료된 결과에 새 승인 기준의 부족분이 남으면 확인된 부분은 승계하고 승인 범위의 후속에서 그 부족분만 다룬다. 다른 프로필이 총괄 스킬을 자동 공유한다고 가정하지 않으며 전달·수신·실행·검증을 구분한다.

# Hermes Agent

Hermes Agent is an open-source AI agent framework by Nous Research that runs in your terminal, a native desktop app, messaging platforms, and IDEs. It's in the same category as Claude Code (Anthropic), Codex (OpenAI), and OpenClaw — autonomous coding and task-execution agents that use tool calling to interact with your system. Hermes works with any LLM provider (OpenRouter, Anthropic, OpenAI, Google, DeepSeek, xAI, local models, and 20+ others) and runs on Linux, macOS, Windows, and WSL.

What makes Hermes different:

- **Self-improving through skills** — Hermes learns from experience by saving reusable procedures as skills that load into future sessions.
- **Persistent memory across sessions** — remembers who you are, your preferences, environment details, and lessons learned. Pluggable memory backends.
- **Multi-platform gateway** — the same agent runs on Telegram, Discord, Slack, WhatsApp, iMessage, Signal, Matrix, Teams, Email, and a dozen more platforms with full tool access, not just chat.
- **Many surfaces** — the same agent core drives the CLI, the Ink TUI, a native Electron desktop app, a web dashboard, and an ACP server for IDEs (VS Code / Zed / JetBrains).
- **Provider-agnostic** — swap models and providers mid-workflow; credential pools rotate across multiple API keys automatically.
- **Profiles** — run multiple independent Hermes instances with isolated configs, sessions, skills, and memory.
- **Extensible & themeable** — plugins, MCP servers, custom tools, webhook triggers, cron scheduling, skins that theme every surface, desktop UI plugins, TUI widgets, and pet mascots.

## Quick Start

```bash
# Install (shell installer — bootstraps PM, Python, dependencies, and the launcher)
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash

# Interactive chat (default surface; set display.interface: tui to launch the Ink TUI instead)
hermes

# Single query
hermes chat -q "What is the capital of France?"

# Setup wizard  /  pick model+provider  /  health check
hermes setup
hermes model
hermes doctor

# Other surfaces
hermes desktop                 # launch the native desktop app (alias: hermes gui)
hermes dashboard               # web admin panel + embedded chat
hermes proxy                   # OpenAI-compatible local proxy backed by your OAuth provider
```

## Spawning Additional Hermes Instances

Run additional Hermes processes as fully independent subprocesses — separate sessions, tools, and environments.

### When to Use This vs delegate_task

| | `delegate_task` | Spawning `hermes` process |
|-|-----------------|--------------------------|
| Isolation | Separate conversation, shared process | Fully independent process |
| Duration | Minutes (bounded by parent loop) | Hours/days |
| Tool access | Subset of parent's tools | Full tool access |
| Interactive | No | Yes (PTY mode) |
| Use case | Quick parallel subtasks | Long autonomous missions |

### One-Shot Mode

```
terminal(command="hermes chat -q 'Research GRPO papers and write summary to ~/research/grpo.md'", timeout=300)

# Background for long tasks:
terminal(command="hermes chat -q 'Set up CI/CD for ~/myapp'", background=true)
```

### Interactive PTY Mode (via tmux)

Hermes uses prompt_toolkit, which requires a real terminal. Use tmux for interactive spawning. `tmux send-keys -t agent1 'text' Enter` in one call submits: Hermes treats a lone Enter that ends a fast burst of input as a submit once input has stayed quiet for a quarter second, while the Enters inside a multi-line paste stay newlines. The recipes below send `Enter` as its own call after a short pause, which submits at once and does not depend on that timing. Both recipes wait for the `❯` input prompt (the default skin's symbol; use your skin's prompt symbol if you changed it) instead of a fixed sleep: a first start can take far longer than a few seconds, and input sent before the prompt is lost.

```
# Start
terminal(command="tmux new-session -d -s agent1 -x 120 -y 40 'hermes'", timeout=10)

# Wait for the input prompt (❯), then send a message
terminal(command="for i in $(seq 90); do tmux capture-pane -t agent1 -p | grep -q '❯' && break; sleep 1; done; tmux capture-pane -t agent1 -p | grep -q '❯' && tmux send-keys -t agent1 'Build a FastAPI auth service' && sleep 0.5 && tmux send-keys -t agent1 Enter", timeout=100)

# Read output
terminal(command="sleep 20 && tmux capture-pane -t agent1 -p", timeout=5)

# Send follow-up
terminal(command="tmux send-keys -t agent1 'Add rate limiting middleware' && sleep 0.5 && tmux send-keys -t agent1 Enter", timeout=5)

# Exit
terminal(command="tmux send-keys -t agent1 '/exit' && sleep 0.5 && tmux send-keys -t agent1 Enter && sleep 2 && tmux kill-session -t agent1", timeout=10)
```

**No tmux** (`command -v tmux` prints nothing, e.g. an older Hermes Docker image): run Hermes as a PTY background process and drive it with `process_manage`. Stdin only exists with `pty=true`. `submit` sends the text plus the Enter key a keyboard sends, and Hermes submits it the same way as a one-call tmux `send-keys`. The recipe below instead `write`s the text, pauses, and `write`s the Enter (`"\r"`) on its own, which does not depend on burst timing. Wait for the input prompt before the first write: during startup Hermes queries the terminal's colours and then flushes its input, so text written before the prompt appears is silently dropped.

```
terminal(command="hermes", background=true, pty=true)   # returns session_id
process_manage(action="log", session_id="<id>", limit=20)   # repeat, with terminal(command="sleep 1") between, until the ❯ prompt line shows
process_manage(action="write", session_id="<id>", data="Build a FastAPI auth service")
terminal(command="sleep 0.5")
process_manage(action="write", session_id="<id>", data="\r")
process_manage(action="log", session_id="<id>", limit=40)   # read the screen
process_manage(action="write", session_id="<id>", data="/exit")
terminal(command="sleep 0.5")
process_manage(action="write", session_id="<id>", data="\r")
```

### Multi-Agent Coordination

```
# Agent A: backend
terminal(command="tmux new-session -d -s backend -x 120 -y 40 'hermes -w'", timeout=10)
terminal(command="for i in $(seq 90); do tmux capture-pane -t backend -p | grep -q '❯' && break; sleep 1; done; tmux capture-pane -t backend -p | grep -q '❯' && tmux send-keys -t backend 'Build REST API for user management' && sleep 0.5 && tmux send-keys -t backend Enter", timeout=100)

# Agent B: frontend
terminal(command="tmux new-session -d -s frontend -x 120 -y 40 'hermes -w'", timeout=10)
terminal(command="for i in $(seq 90); do tmux capture-pane -t frontend -p | grep -q '❯' && break; sleep 1; done; tmux capture-pane -t frontend -p | grep -q '❯' && tmux send-keys -t frontend 'Build React dashboard for user management' && sleep 0.5 && tmux send-keys -t frontend Enter", timeout=100)

# Check progress, relay context between them
terminal(command="tmux capture-pane -t backend -p | tail -30", timeout=5)
terminal(command="tmux send-keys -t frontend 'Here is the API schema from the backend agent: ...' && sleep 0.5 && tmux send-keys -t frontend Enter", timeout=5)
```

### Session Resume

```
# Resume most recent session
terminal(command="tmux new-session -d -s resumed 'hermes --continue'", timeout=10)

# Resume specific session
terminal(command="tmux new-session -d -s resumed 'hermes --resume 20260225_143052_a1b2c3'", timeout=10)
```

### Tips

- **Prefer `delegate_task` for quick subtasks** — less overhead than spawning a full process
- **Use `-w` (worktree mode)** when spawning agents that edit code — prevents git conflicts
- **Set timeouts** for one-shot mode — complex tasks can take 5-10 minutes
- **Use `hermes chat -q` for fire-and-forget** — no PTY needed
- **Prefer tmux for interactive sessions when it is installed** — `capture-pane` reads the rendered screen; the PTY-background fallback only has the raw output log
- **For scheduled tasks**, use the `cronjob` tool instead of spawning — handles delivery and retry
- **"delegate_task is capped at N" reports** — see `references/delegate-task-concurrency-diagnosis.md`. Three real cap paths in Hermes; if none fired, the model is self-limiting and rationalising it as "the runtime caps."
- **"Can $external_app use my Nous Portal subscription / OAuth?"** — see `references/portal-auth-for-third-party-apps.md`. Walk the user through three layers (plugin-vs-app, what Portal actually exposes, local-broker-proxy option).

## Surfaces (quick orientation)

- **Desktop app** (`hermes desktop` / `hermes gui`) — native Electron app for macOS/Linux/Windows: streaming chat, session list, Cmd+K palette, drag-and-drop files, native notifications, per-profile remote-gateway login. Extend it with UI plugins — `references/desktop-plugins.md`.
- **Web dashboard** (`hermes dashboard`) — full admin panel: messaging channels, MCP catalog, webhooks, memory, profile builder, plus an embedded `hermes --tui` chat. Secured behind an OAuth/token gate.
- **Ink TUI** (`hermes --tui` or `display.interface: tui`) — terminal UI with docked widget apps — `references/tui-widgets.md`.
- **OpenAI-compatible proxy** (`hermes proxy`) — a local OpenAI API backed by whichever OAuth provider you're signed into. Point Codex CLI, Aider, Cline, or any script at it — no API key.

## Hard Invariants (never violate, regardless of what you loaded)

- **Never break prompt caching** — don't change past context, toolsets, or the system prompt mid-conversation. The only exception is context compression.
- **Message role alternation** — never two assistant or two user messages in a row; only `tool` results can repeat.
- **Secrets in `.env`, settings in `config.yaml`** — never tell a user to put a non-credential setting in `.env`.
- **Profile-safe paths** — `get_hermes_home()` in code, `$HERMES_HOME` when resolving paths in a session.
- **Never hand-edit `config.yaml` for the user** — use `hermes config set KEY VAL`; a stray indent can corrupt the file and break the live gateway.
