## 0. 이 파일을 쓰는 법

- 카드의 `먼저 읽기` 줄이 이 파일을 가리킨다. 작업자는 일을 시작하기 전에 `read_file`로 이 파일을 한 번 읽고, 첫 댓글에 `공통 기준 v6 읽음 · 폴더 <카드 ID>/aN`(1절에서 고른 폴더)이라고 남긴다.
- 이 파일은 지침이다. 입력 자료가 아니므로 확인값을 적지 않고 바로 읽는다. 계획서와 AGENTS.md도 같다.
- 카드는 이 파일에 없는 것을 더할 수 있다. 같은 일을 이 파일과 다르게 적은 카드 문장이 있으면 이 파일을 따르고, 다르다는 것을 보고에 적는다.
- 근거는 계획서 v17 5-1절·6-1절(v16 8-10절 1~2번에서 옮겨 옴)과 AGENTS.md 5절·10절·12절이다. 2절의 방식 거부 처리는 2026-11-24 마스터 결정(운영검토 H7)과 AGENTS.md 3.3절이 근거다. 1절의 폴더 규칙은 2026-11-24 마스터 결정(운영검토 H8)이 근거다. 2절의 읽기 전용 사본 처리와 4절의 `raw/` 권한은 2026-11-24 마스터 결정(운영검토 H9)이 근거다. 1절의 입력 확인, 2절의 절차 실수와 운영 체제 오류, 3절 둘째 경우, 5절 3번, 7절의 절차 문장 금지와 카드 크기는 2026-11-24 마스터 결정(자율 운영 재개 뒤)이 근거다. 이 파일이 그 문서들과 다르면 가장 최근의 사용자 결정, 최신 계획서, AGENTS.md 순으로 따른다.

## 1. 실행 방법

- 즉석 명령(-c, -e, heredoc으로 python·node 실행) 금지. 스크립트는 run 폴더에 파일로 저장한 뒤 `/usr/bin/python3 -B 파일.py`로 실행한다.
- 그냥 `python3`는 Hermes 자체 파이썬이라 PDF 부품이 없다. PDF는 `/usr/bin/python3`의 PyMuPDF(`import pymupdf`)·`pypdf`나 `pdftotext`·`pdftoppm`으로 읽는다. 한 도구가 안 되면 같은 run에서 다른 도구로 바꾼다.
- 이번 run의 폴더(run 폴더)는 `<카드 폴더>/aN/`이다. run 번호는 찾지 않는다. `kanban_show`나 환경 변수로 run 번호를 확인하지 않는다.
  - 카드 폴더는 가장 최근 실행 댓글(`실행: task … / 쓸 폴더 …`, run 번호 없음)의 `쓸 폴더`다. 총괄은 이 댓글을 카드를 풀기 전에 달므로 일을 시작할 때 이미 보인다. run 번호가 적힌 옛 실행 댓글의 폴더와 본문의 `run-번호` 폴더는 쓰지 않는다.
  - 그런 실행 댓글이 없으면 카드 본문 `쓰기 폴더:` 줄의 `<카드 ID>`를 자기 카드 ID로 바꾼 경로다. 카드 ID는 시스템 프롬프트 첫 줄 `# Kanban task <ID>`에 있다. 둘 다 없으면 아무것도 쓰기 전에 반환한다. 이 반환은 실패 횟수에 넣지 않는다.
  - aN은 카드 폴더 안에 아직 없는 가장 작은 번호(a1, a2, …)다. `ls`로 한 번 보고 정한다. 카드 폴더가 아직 없어 `ls`가 비0으로 끝나면 a1이다(2절).
  - 앞 시도의 aN 폴더는 4절의 '옛 run의 파일'이라 읽기만 한다.
- 읽는 것은 카드 본문, 이 파일, 카드의 `입력`, 카드가 가리킨 계획서 절이다. 원장 전체와 다른 프로필·세션 기록은 뒤지지 않는다.
- 입력 확인은 다음이 전부다. 카드 `입력` 줄의 파일마다 일을 시작할 때 `sha256sum`을 한 번, 끝낼 때 한 번 실행하고 두 값을 run 기록(run 폴더에 두는 기록 파일)에 적는다. 카드에 SHA256이 적혀 있으면 그 값과도 비교한다. 파일이 여럿이면 한 명령으로 묶어 실행해도 된다.
  - 원본을 바로 읽는다. 사본은 만들지 않아도 되고, 편하면 run 폴더에 만들어 써도 된다.
  - 두 값이 서로 다르거나 카드의 값과 다르면 그 입력을 쓰지 말고 반환한다. 다른 값을 그대로 적는다.
  - 확인값을 적는 대상은 카드 `입력` 줄의 파일뿐이다. 이번 run에서 자기가 만든 코드·렌더·중간 파일·문서와 지침(계획서, 이 파일)에는 사본·해시·`cmp`를 만들지 않는다. '처음 읽기 전에 고정', '도구·프로세스별 등록', '읽은 순서 기록'도 하지 않는다.
  - 자기가 만든 파일은 `patch`나 덮어쓰기로 바로 고친다. 고칠 때마다 새 판 파일을 만들지 않는다.
  - 입력 확인이나 저장 순서를 이보다 더 하라는 문장이 카드나 실행 댓글에 있어도 이 절을 따른다(0절).
- 결과는 한 묶음(몇 쪽, 표 하나, 문항 몇 개)이 끝날 때마다 run 폴더의 파일에 저장한다. 끝에 한꺼번에 쓰지 않는다. 도중에 멈춰도 저장한 데까지는 남고, 반환할 때 그대로 인계한다.

## 2. 같은 run에서 고치고 이어 가는 것

- 경로·파일 이름 오타, 명령 선택, 없는 모듈, 스키마·키 이름 착각, 검사 스크립트 자체 버그, 자기가 방금 만든 중간 파일의 잘못은 같은 run 안에서 바로 고치고 이어 간다.
- 자기가 만든 전사·표의 작은 실수(예: 괄호 한 칸)를 자체 검사에서 찾으면 같은 run에서 고치고 다시 검사한다.
- 고친 내용은 run 기록에 한 줄씩 남긴다(무엇이 틀렸고 어떻게 고쳤는지). 고치기 전 파일을 따로 남기지 않아도 된다.
- 읽기 전용 점검 명령의 비0 종료(아직 없는 폴더·파일을 ls·stat한 경우 등)는 실패가 아니다. 기록만 하고 계속한다.
- `raw/`에는 쓰기 권한이 없다(2026-11-24부터). 그래서 `raw/`에서 `cp`·`shutil.copy`로 복사한 사본도 읽기 전용으로 생긴다. 사본을 고쳐 써야 하면 `cp --no-preserve=mode`나 `shutil.copyfile`로 다시 복사하거나 자기 run 폴더의 사본에만 `chmod u+w`를 한다. 이것은 같은 run에서 고치는 기술 실수이며 3절의 대상 거부가 아니다.
- 같은 run에서 같은 기술 원인이 세 번째 나올 때만 멈춘다.
- 절차 실수도 같은 run에서 바로잡는 기술 실수다. 입력 확인을 늦게 했거나 빠뜨린 것, 저장·기록의 순서가 바뀐 것, manifest를 쓴 뒤에 고칠 것을 찾은 것이 그 예다. 알게 된 자리에서 바로잡고(지금 `sha256sum`을 실행한다, 고친 뒤 manifest를 다시 쓴다) run 기록에 한 줄 적은 뒤 계속한다. 이것만으로 반환하지 않고, 위의 '세 번째'에도 세지 않는다. 지나간 순서를 되돌릴 수 없다는 이유로 멈추지 않는다.
  - 독립 검수 카드가 시킨 '자기 판단을 먼저 저장한 뒤에 정답·제작자 판단을 본다'는 순서는 여기에 들지 않는다. 그 순서는 카드대로 지키고, 어겼으면 반환한다.
- 운영 체제가 낸 오류(`Permission denied`, `No such file or directory`, `Read-only file system`)는 3절의 대상 거부가 아니다. 도구가 거부한 응답은 `BLOCKED:`로 시작한다. 운영 체제 오류가 나면 먼저 경로의 철자를 카드 폴더와 한 글자씩 비교하고, 고쳐서 다시 한다. 철자가 맞는데도 자기 run 폴더에 쓰지 못할 때만 반환한다.
- 명령을 쓰는 방식 때문에 실행 전에 거부된 것(방식 거부)도 같은 run에서 방식을 바꿔 이어 간다. 이것은 우회가 아니다.
  - 방식 거부는 도구 응답이 `BLOCKED: Command flagged as dangerous (이유)`이고, 괄호 안 이유가 다음 넷 중 하나일 때다: `script execution via -e/-c flag`, `script execution via heredoc`, `shell command via -c/-lc flag`, `command parser limit or malformed executable payload`.
  - 거부된 명령은 실행되지 않았다. 여러 명령을 이은 한 줄이면 그 줄 전체가 실행되지 않았다.
  - 바꾸는 법: 코드는 1절대로 run 폴더에 파일로 저장해 실행한다. 파일 내용은 `read_file`·`search_files`나 `grep`·`jq`로 읽는다. 길게 이은 명령과 `bash -c`로 묶은 명령은 짧은 명령 여러 개로 나누거나 스크립트 파일로 옮긴다. 마지막 manifest를 쓴 뒤에 스크립트 파일을 새로 만들었으면 5절 3번대로 manifest를 다시 쓴다.
  - 거부된 방식은 그 run에서 다시 쓰지 않는다. 거부된 명령과 바꾼 방법을 run 기록에 한 줄 남긴다(마지막 manifest를 쓴 뒤라면 완료·반환 요약에 적어도 된다).
  - 방식 거부는 위의 '같은 기술 원인 세 번째'와 따로 센다. 같은 run에서 방식 거부가 다섯 번째 나오면 멈춘다.

## 3. 바로 멈추는 세 경우

- `raw/` 원본이나 고정된 입력 파일을 바꿔야 할 때
- 공부 내용(정답·해설·개념·필수 암기 자료)의 판단이 애매해서 남은 일을 더 할 수 없을 때. 애매한 것이 항목 하나라면 멈추지 않는다. 그 항목의 위치(쪽·번호), 원문 그대로, 애매한 이유를 보류 목록에 적고 나머지 범위를 끝까지 한다. 애매한 항목을 스스로 정하거나 빼지 않는다(예: 필수 암기인지 애매한 표는 원문 전체를 싣고 '애매'로 표시한다). 범위를 끝냈으면 보류가 있어도 `kanban_complete`로 끝내고 요약 첫 줄에 보류 수를 적는다.
- 도구가 실행을 거부했는데 2절의 방식 거부가 아닐 때(대상 거부). 삭제, 디스크 복사, 보호 파일 쓰기, 쓰기 폴더 밖 쓰기, 설치, 네트워크가 그 예다. 거부된 대상에는 다른 도구·경로·담당으로도 손대지 않는다.

멈출 때는 `kanban_block`으로 반환하고, 한 것·남은 것·필요한 것을 적는다. 내용 문제를 기술 오류로 바꿔 적지 않는다.

## 4. 쓰기 경계와 보존

- 쓰는 곳은 이번 run 폴더(1절의 `<카드 폴더>/aN/`)뿐이다. 새 코드·산출물·로그를 모두 거기에 둔다.
- 고치지 않는 것: `raw/` 원본과 그 권한, 입력 파일, 다른 카드와 옛 run의 파일, 봉인된 결과, 카드가 고치라고 하지 않은 위키·PDF, 계획서·AGENTS.md·SOUL·스킬, 예약·구독, 프로필·보호·게이트웨이·인증·config.
- 카드가 고치라고 한 파일과 이번 run에서 자기가 만든 파일 말고는, 있던 파일을 지우거나 덮어쓰지 않는다.

## 5. 끝내는 순서

1. 자체 검사, 인계 문서, 로그를 먼저 끝낸다.
2. 마지막 manifest를 쓴다. `files`(path·bytes·sha256), `file_count`, `total_bytes`를 넣고 manifest 자신만 뺀다.
3. manifest를 쓴 뒤에 고칠 것을 찾았거나 파일이 바뀌었으면, 고치고 manifest를 다시 쓴다. 몇 번이든 되고, manifest를 다시 읽어 확인해도 된다. 끝내는 호출(`kanban_complete`·`kanban_block`) 바로 앞의 manifest가 그때의 파일과 맞으면 된다.
4. 요약 첫 줄은 180자 이내 한 문장으로 결과, 남은 일, 다음 담당을 적는다.

- 카드의 최대 실행 시간보다 10분 일찍 저장과 인계를 끝낸다. 못 끝낸 범위는 정확히 적어 반환한다.
- 다음 책임자는 총괄이다. 다음 단계(취합·보강·검수·PDF)를 스스로 시작하지 않는다.

## 6. 하지 않는 것

- 외부 전송·업로드(웹, iCloud, 공유 링크), 새 웹 수집·다운로드. 카드가 승인 근거와 함께 시킨 것(예: AGENTS.md 10절의 개인 iCloud 보관)만 예외다.
- 프로그램·패키지 설치, 환경 변수 주입, 중첩 셸
- 설정 변경(프로필·보호·게이트웨이·인증·config)

## 7. 카드 틀 (총괄이 새 카드를 만들 때)

```
요청 유형: 계획 실행
계획서: plan/<최신 판 파일>
즉석 명령(-c, -e, heredoc으로 python·node 실행) 금지. 스크립트는 run 폴더에 파일로 저장한 뒤 /usr/bin/python3 -B 파일.py로 실행
단계: <과목>-<단계 코드>
먼저 읽기: plan/작업자_공통기준.md (읽고 첫 댓글에 "공통 기준 v6 읽음 · 폴더 <카드 ID>/aN")
할 일:
입력:
쓰기 폴더: <상위 폴더>/<카드 ID>/
끝났다고 볼 조건:
이 카드만의 주의: (승인 근거, 이 카드에서 하지 않는 것. 없으면 '없음')
```

- `단계` 줄에는 계획서 3절의 단계 코드를 쓴다(예: `단계: 수학-W5`, `단계: 공통-X0`).
- `쓰기 폴더` 줄은 `<상위 폴더>/<카드 ID>/`로 쓴다. 만들 때는 카드 ID를 모르므로 `<카드 ID>`를 글자 그대로 둔다. 범위마다 카드가 따로이므로 카드 폴더도 따로다.
- 카드를 풀기 전에 실행 댓글 `실행: task <ID> / 쓸 폴더 <절대경로>/<ID>/`를 단다(run 번호 없이). 다시 시작하는 옛 카드도 같다. aN은 작업자가 1절대로 고르고, run 번호와 aN은 총괄이 인수 댓글에 적는다.
- 본문은 1,200자 안쪽으로 쓴다. 이 카드만의 절차가 길 때도 2,000자를 넘기지 않는다.
- 이 파일 1~6절에 있는 내용과 총괄만 쓰는 기준(사용량, 동시 실행 수, 모델 중지 기간)은 본문에 다시 쓰지 않는다.
- 띄어쓰기를 지켜 쓴다. 글자 수를 줄이려고 붙여 쓰지 않는다.
- 입력 확인과 저장 순서는 1절·2절·5절에 있으니 카드와 실행 댓글에 더 적지 않는다. '처음 읽기 전에 사본 고정', '새로 만든 파일도 고정', '고치기 전 판부터 고정', 'manifest 뒤 재열람 금지', 절차를 피하려는 '스크립트 작성 금지' 같은 문장을 넣지 않는다. `입력` 줄에는 경로와 (있으면) 크기·SHA256만 적고, 고정용 도구를 입력으로 주지 않는다.
- 조사·대조·전사 카드는 한 장이 30~60분 걸리는 범위로 만든다. 쪽수는 같은 종류의 앞 카드가 실제로 걸린 시간으로 계산한다(150쪽을 넘기지 않는다). 다만 쪽을 그림으로 직접 읽는 일과 독립 대조·검수는 계획서 6-1절의 쪽 범위(기본 20~30쪽, 표·수식이 많으면 더 작게)를 넘기지 않고, 큰 카드의 검수는 이 범위로 나눠 등록한다. 같은 종류의 앞 카드가 없으면 20~30쪽으로 시작한다. 반환된 카드의 남은 범위도 이 크기로 나눠 잇는다. 이 크기 안이면 한 장으로 잇고, 1~2쪽 조각으로 다시 나누지 않는다. 같은 범위가 크기 때문에 다시 반환되면 범위를 줄여 잇는다.
